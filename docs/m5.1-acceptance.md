## 2. 实现结果

### 2.1 设置弹窗与主页签

- 主面板只保留四个页签：状态、主动性 / 提醒、记忆、审计 / 事件；原来的设置页签和 `tab-settings` 内容已删除。
- 顶部新增“设置”按钮和常驻 QQ 状态 badge。badge 使用 `aria-live="polite"`，与设置页共用同一个状态接口。
- 设置使用原生 `<dialog>`，左侧为“模型接入”和“QQ 渠道”两个真实页面；没有空占位页。
- 桌面弹窗宽度 `1040px`，高度受视口约束；内容区是唯一滚动容器。移动端弹窗全屏，导航变为顶部两列。
- Esc 和遮罩点击都能关闭设置；关闭事件把焦点送回“设置”按钮。
- 模型与 QQ 设置分别请求、分别显示错误，一个接口失败不会阻断另一个。
- 页面标题和 eyebrow 更新为 M5.1；聊天、审计继续保持固定高度独立滚动。

### 2.2 QQ / NapCat 设置

- 新增 `ChannelSettingsService`，页面可查看和修改：开关、WebSocket URL、远程许可、私聊/群白名单、群 @、主动目标、超时、重连、去重保留期、聚合、图片、拆条和限频参数。
- `autonomous_target` 下拉只列出当前白名单中的目标；手填 QQ 号列表会规范化、去重并校验 5～20 位数字。
- 高级参数放在可折叠区域，但仍是真实可编辑字段；默认值与 `config/examples/channels.toml` 共用同一套 schema。
- 新增 HTTP：
  - `GET /kanobot/api/settings/channels`
  - `PUT /kanobot/api/settings/channels`
  - `POST /kanobot/api/settings/channels/test`
  - `GET /kanobot/api/settings/channels/status`
- 接口复用宿主 Cookie/会话鉴权、同源检查和有限的 JSON body 大小；PUT 拒绝未知字段，示例配置目录只读。
- 保存后只显示“配置已保存；重启 DSH 后 QQ 渠道生效”，不会刷新成伪造的已连接状态。
- 设置页和顶部 badge 使用同一状态映射：未配置、未启用、连接中、已连接、重连中、已停止、连接错误；没有 selfId 时不显示“已连接”。
- 连接测试使用当前表单草稿，不保存配置；只做 OneBot WebSocket 握手和 `get_login_info`，不发送任何 QQ 消息。401/403、超时、非法 URL 和非法响应都映射为稳定错误码。

### 2.3 运行时覆盖与凭据

- 新增 `channel-settings.json` 运行时覆盖：设置页写出完整的 `qq` 段，启动时整体覆盖 `channels.toml` 的 `qq` 段。覆盖文件存在时不需要 TOML 也能单独生效。
- TOML 与 JSON 覆盖最终都由 `validateChannels` 校验；覆盖文件 JSON 损坏、字段未知或类型错误时 fail-closed，不回退到旧 TOML。
- 保存先写同目录临时文件，再原子替换；写后重新加载配置验证。失败时删除新 secret、恢复旧 overlay；旧 token 只在新配置成功后才清理。
- 凭据来源支持：保留当前、清空、环境变量、本地密钥。环境变量与 `access_token_secret` 互斥；远程 `ws://` 被拒绝，远程目标必须有 token 来源。
- 本地密钥复用 `LocalSecretStore`，label 为 `kanobot-qq`。页面只知道“未配置 / 环境变量 NAME / 本地密钥已保存”，不返回 token 或 `secret_...` 引用。
- 密码框只写入、不回显；`channel-settings.json`、SQLite、审计、日志和 API 响应均不保存 token 明文。
- 开发入口也挂载了只读示例的 QQ 设置/状态接口，避免 `npm run dev` 的设置页出现空壳；正式保存仍由独立程序和 DSH 插件提供。

### 2.4 低摩擦提醒

- 明确委托：当前用户消息包含提醒/叫我/通知我/别忘了等委托词，模型给出至少一个合法未来 `dueAt`，且事项和时间清楚时，直接创建 active 提醒，`remindersActivated` 计数增加。
- 模糊委托：时间或内容不明确时保留 pending 候选；下一轮“可以 / 好 / 确认 / 就这样 / 没问题”自动确认最近一条同会话候选，“不要 / 不用 / 取消 / 算了”拒绝。
- 确认 TTL 为约 30 分钟；更早的 pending 不会被一句无关的“可以”确认。
- 同会话多条 pending 不会批量猜测，系统返回 `reminder_confirmation_ambiguous`，仍要求用户指定。
- 用户没有明确委托时，模型推断出的提醒候选被确定性拒绝，只留脱敏审计码，不变成 active 或 pending。
- 确认轮即使模型错误地再次返回候选，也不会新建重复提醒。
- 去重同时查看同会话 pending 和未送达 active 提醒；直接提醒 ID 含会话摘要，确认候选通过来源映射反查，避免不同会话误合并。比较动作核心与相近时间，不把同一时间的“洗澡”和“喝水”合并。
- STOP 状态下明确委托也只保留 pending 并记录 `reminder_activation_stopped`，聊天确认同样不能绕过 STOP。
- 聊天页分别显示“已自动设置 N 条提醒”和“新增 N 条待确认提醒”；提醒页 badge 同时统计 pending 候选和已确认/排队中的 active 提醒。
