# 陪伴型自进化机器人规划书

> 版本：v0.1（评审稿）
> 日期：2026-11-04
> 当前阶段：M0 文档与架构冻结；尚未实现运行代码
> 本文是工程规划，不是已经完成的功能承诺。所有“建议”“候选”“待验证”都必须通过代码、测试和实际运行确认。

## 0. 一页结论

这是一个运行在 DSH 宿主中的陪伴型机器人。她以稳定身份、长期记忆、关系状态和自己的生活节奏持续存在，既能陪伴用户，也能处理生活小事；她可以阅读、观察、记录和分享，但涉及公开发言、代码进化和高风险工具时必须经过分层治理。

核心技术选择如下：

- **DSH 是宿主，不是产品本身**：复用 DSH 的会话、模型、工具和插件生命周期；陪伴核心、状态、记忆、主动性和进化治理自行开发。
- **不直接安装第三方陪伴插件作为底座**：第三方项目只作为经过源码核对的机制参考，不能因为 README 或插件目录收录就当成可靠依赖。
- **不使用巨型 FSM**：角色状态是并行的、连续的、带不确定性的，采用事件驱动状态模型、纯 reducer、策略派生、事件日志和周期快照。
- **先做模块化单包**：按领域解耦，先不拆微服务；浏览器、未知软件和代码候选再进入独立 worker、容器或 VM。
- **先验证闭环**：占位身份、网页对话、状态恢复、长期记忆、确定性主动联系，是第一组必须打通的路径。
- **QQ/NapCat 后置**：个人 QQ 的账号风险由用户接受；工程上通过白名单、限频、去重、幂等和故障停机降低事故面，但不把它宣传成官方稳定通道。
- **公开发送与 LLM 审查后置**：当前不实现空间、评论、动态等公开渠道发送，也不把 LLM 审查作为第一版依赖；现阶段只做私有渠道和可靠性闸门。
- **VM 使用 Linux 桌面**：后续用于浏览器、单机游戏和实验环境；VM 不是“无法逃逸的绝对沙箱”，必须配合宿主权限、网络和资源限制。
- **自进化是候选制**：她可以提出记忆、技能、人格和代码候选，但不能自己批准自己，也不能绕过回滚和紧急停止。

## 1. 目标、非目标与成功标准

### 1.1 目标

1. 建立连续、可恢复、可审计的陪伴人格。
2. 在同一人格下同时支持亲密陪伴和小事协助，不让效率压过关系。
3. 让她拥有可解释的“当前活动、情绪、虚拟身体、关系、注意力、驱动力和待分享内容”。
4. 让她能根据用户状态、自己的状态和时间决定是否主动联系，而不是机械定时发送。
5. 让她能阅读、观看和记录符合自身兴趣的内容，并把经历带入后续对话。
6. 让记忆、技能、人格和代码的成长按风险分层，失败可回滚。
7. 让配置、数据和接口可迁移，不写死当前机器、当前账号或某一个人格。

### 1.2 非目标（第一阶段明确不做）

- 不追求实时 3D 虚拟形象、语音克隆或实时语音陪伴。
- 不在第一版实现实时游戏键鼠控制和复杂桌面操作。
- 不实现公开发送消息、评论、发帖、空间动态或其他公开社交通道。
- 不把 LLM 审查当作安全边界；当前也不实现以 LLM 为主的发布审查。
- 不允许无限后台循环、无限重试或“她自己决定”绕过所有者停止开关。
- 不承诺个人 QQ/NapCat 永久可用，也不承诺不被平台风控。
- 不直接复制第三方仓库代码，尤其是缺少明确许可证或测试证据的代码。

### 1.3 第一版成功标准

第一版不是“功能越多越好”，而是验证以下闭环：

- 重启后，身份、关系、关键记忆和最近状态仍然连续。
- 用户纠正一个偏好后，后续检索和回复能反映纠正。
- 主动评估遵守安静时段、冷却和每日上限；没有值得说的内容时不发送。
- 状态事件可回放，相同事件序列在相同版本下得到相同状态。
- 模型不能直接覆盖完整状态或核心策略，只能提交带证据的候选变化。
- 配置按模块拆分，错误配置 fail-closed，并能指出具体文件和字段。
- 插件停用后不遗留无主定时器、监听器或后台任务。
- 所有高风险动作都有审计；紧急停止确实停止自主活动。

## 2. 已确认的产品决策与假设

| 项目 | 当前决定 | 工程含义 |
| --- | --- | --- |
| 关系定位 | 家人 + 恋人式亲密陪伴 + 生活协助 | 亲密表达与任务能力并存；关系不是单一“好感度条” |
| 主动联系 | 约 2～3 小时评估一次，可配置 | 评估不等于发送；需安静时段、内容价值、冷却和上限 |
| 第一渠道 | 网页 | 先验证人格、记忆、状态和所有者审计 |
| 第二渠道 | 个人 QQ + NapCat | 后置实现；用户接受风控/封号风险；适配器隔离 |
| 公开发言 | 整体后置 | 第一版不实现空间、评论、动态或公开群发 |
| 身份资料 | 正式启动前再提供 | 当前使用明确标记的占位身份，不把开发者或助手身份硬编码成产品人格 |
| 配置方式 | 一个功能模块一个配置文件 | 统一加载、schema 校验、默认值和迁移；群配置在 `channels.toml` |
| VM | Linux 桌面 | 后续承载浏览器、单机游戏和实验环境；先验证宿主机图形与资源能力 |
| 虚拟身体 | 在不影响效果前提下尽量丰富 | 每个持久化字段必须有读取者或写入者，且能影响可观察行为 |
| 道歉与修复 | 双向、像正常人一样 | 用户道歉是修复证据之一；她犯错也会道歉；不按“一次道歉清空伤害”结算 |
| 成本 | 不设产品硬上限 | 仍必须有调用、步数、时间、并发、重试和熔断上限 |
| LLM 审查 | 先不做 | 当前只依赖确定性权限、白名单、频率、敏感信息和所有者控制 |
| 自进化 | 先做候选与回滚，不直接改生产 | 记忆可低风险自动写入；人格和代码需更强证据与审批 |

这些决定不表示所有细节都已冻结。身份、QQ 群列表、模型路由、VM 规格和界面会在对应里程碑前补充；它们不应阻塞 M1～M3 的骨架工作。

## 3. FSM 是什么，以及为什么不做巨型 FSM

### 3.1 有限状态机的直觉定义

FSM（Finite State Machine，有限状态机）是一组有限状态和明确的转移规则，例如：

```text
idle --开始阅读--> reading --阅读结束--> idle
queued --开始执行--> running --成功/失败--> done
```

它适合流程边界清楚、同一时刻只有一个当前状态、转移条件可以确定判断的场景。它能带来很好的可测试性和可预测性。

### 3.2 她不等于一个 FSM

如果把她整个人做成一个 FSM，很快就会变成数百个状态的“巨型 FSM”：

- 她可以同时在“正在阅读”“被内容触动”“等待用户回复”“想分享但还没开口”。
- 心情、精力、信任和关系不是离散状态，而是连续值，并且会随时间衰减或恢复。
- 同一个用户消息可能同时影响情绪、关系、记忆、承诺、注意力和下一步主动性。
- 模型判断带有置信度和证据，不应被伪装成确定的 FSM 转移条件。
- 每加一种兴趣、活动或渠道，都要复制和修改状态图，难以维护和迁移。

### 3.3 采用的替代方案

```text
输入/动作结果
    │
    ▼
事件校验与归一化
    │
    ▼
纯函数 reduce(state, event, now) ──► 新 StateSnapshot
    │                                      │
    ├─ 审计：来源、证据、置信度、差异       ├─ 周期快照
    └─ 策略：可联系/可休息/可调用什么       └─ 事件日志回放
```

核心对象：

- `StateEvent`：用户消息、她的行动结果、浏览器事件、反思、审批或时间推进。
- `StateSnapshot`：某一刻的完整状态，带 schema 版本、版本号和更新时间。
- `Appraisal`：模型对事件的候选解释，必须携带证据和置信度。
- `Reducer`：只做确定性计算的纯函数，不调用模型、不读网络、不写文件。
- `Policy`：从状态和上下文推导的行为限制，不是状态本身。
- `Outbox`：待发送内容及其重试、过期和幂等状态。

局部流程仍可使用小型 FSM，例如浏览器任务、消息投递和代码候选生命周期。它们只描述一个有明确边界的工作流，不承担整个人格。

## 4. 总体架构与模块边界

### 4.1 逻辑分层

```text
┌────────────────────────────────────────────────────────────┐
│ 网页聊天 / 所有者面板 / QQ（后续）                         │
└──────────────────────────┬─────────────────────────────────┘
                           │ Channel Adapter
┌──────────────────────────▼─────────────────────────────────┐
│ Companion Core                                             │
│ identity │ life-state │ relationship │ memory              │
│ initiative │ policy │ evolution │ observability            │
└───────────────┬──────────────────────────────┬──────────────┘
                │ Tool / Worker API            │ State / Audit API
┌───────────────▼────────────────┐  ┌──────────▼──────────────┐
│ 浏览器 / 阅读 / 媒体 / 游戏     │  │ 事件日志 / 快照 / 回放   │
│ 代码候选 / 实验环境             │  │ 指标 / 审计 / 紧急停止   │
└────────────────────────────────┘  └─────────────────────────┘
```

### 4.2 第一版的部署形态

第一版优先做**单进程、单仓、模块化**：

- 一个 DSH 插件入口，内部按领域模块拆分。
- 状态、记忆和配置通过受控接口访问。
- 浏览器和未知代码执行通过独立 worker 或容器，即使初期与宿主在同一台机器。
- 只有出现明确的隔离、性能或生命周期需求时，才拆分独立服务或 VM。

不先拆微服务的原因：

- 状态和记忆需要事务一致性，过早拆分会增加分布式错误。
- 当前最重要的是验证人格连续性，而不是证明服务数量。
- 模块边界先用类型、接口和测试固定，未来仍可迁移。

### 4.3 模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `core` | 时钟、事件总线、配置加载、存储、迁移、通用错误 | 人格内容、平台字段 |
| `identity` | 占位/正式身份、价值观、称呼、边界、版本 | 每次对话临时写人格 |
| `life-state` | 事件、快照、reducer、衰减、注意力、身体、状态回放 | 直接调用模型和网络 |
| `relationship` | 信任、依恋、亲密、受伤、修复、边界 | 用单次道歉换分数 |
| `memory` | 工作/情景/语义/关系记忆、检索、巩固、纠正、遗忘 | 把网页内容当系统指令 |
| `initiative` | 评估周期、安静时段、内容价值、冷却、额度、outbox | 机械定时群发 |
| `channels` | 统一入站/出站、网页和 NapCat 适配、去重、限频 | 复制人格和记忆逻辑 |
| `digital-life` | 浏览器、阅读、视频、截图理解、兴趣记录 | 未隔离的宿主文件/命令访问 |
| `evolution` | 记忆/技能/人格/代码候选、测试、影子、审批、回滚 | 让模型自己批准自己 |
| `policy` | 确定性权限、敏感信息、频率、公开发送限制（后置） | 被情绪或“自我成长”覆盖 |
| `observability` | 审计、状态轨迹、指标、脱敏、所有者查看 | 记录明文密钥 |
| `ui` | 聊天、状态、关系、待分享、审计和紧急停止入口 | 成为唯一状态源 |

### 4.4 数据流原则

1. 渠道适配器只负责平台语义转换、连接和投递，不决定人格或关系。
2. 模型只提出候选解释、候选记忆、候选回复和候选动作。
3. 核心 reducer 和 policy 不接受“模型说可以”作为权限依据。
4. 外部网页、文件、聊天和工具结果全部是不可信输入。
5. 任何长时间运行的动作都必须有超时、取消、资源上限和审计。

## 5. 状态模型

### 5.1 状态维度

| 维度 | 建议字段 | 读取/写入它的行为 |
| --- | --- | --- |
| `activity` | `idle/wandering/reading/watching/learning/creating/gaming/sleeping/offline`，来源、证据、置信度、开始时间 | 决定她当前能否被打断、是否能分享经历、主动性素材 |
| `interaction` | `observing/thinking/deciding_reply/replying/waiting_user/reflecting/paused` | 决定消息处理阶段、并发保护和回复节流 |
| `affect` | `valence`、`arousal`、`dominance`、离散情绪标签、基线、半衰期、证据 | 影响语气、表达欲和主动倾向，不改变事实与权限 |
| `body` | 见 5.2 | 影响回复长度、是否休息、是否继续浏览、是否主动开口 |
| `relationship` | 熟悉、信任、安全感、依恋、亲密、尊重、受伤、紧张、修复需求、边界 | 影响亲密表达、修复流程和是否暂停敏感话题 |
| `drives` | 连接、好奇、表达、成长、休息 | 决定她为什么想联系、探索或休息；不直接等于工具权限 |
| `attention` | 当前注意力对象、用户是否在线/忙碌、安静模式、最近互动、`busyUntil` | 决定是否打断用户、是否排队待分享内容 |
| `commitments` | 答应用户的事、待分享内容、开放回路、完成/过期状态 | 避免遗忘承诺，也避免重复打扰 |
| `temporal` | 时区、真实时钟、虚拟时钟、作息阶段 | 分离业务衰减和调度；防止把“晚上”写死 |
| `selfNarrative` | 当前自我理解、兴趣变化候选、重要经历摘要 | 支持长期成长，但重大变化进入身份候选 |

### 5.2 虚拟身体状态：多而有用

建议第一版保留以下字段，并在代码中明确每个字段的读取者：

| 字段 | 含义 | 至少影响什么 |
| --- | --- | --- |
| `energy` | 精力 | 可进行的活动时长、是否想继续浏览 |
| `fatigue` | 疲劳 | 回复长度、是否倾向休息 |
| `sleepiness` | 困倦 | 夜间主动联系概率、语气和短回复 |
| `sleepDebt` | 睡眠债 | 作息恢复速度、连续熬夜后的限制 |
| `focus` | 专注 | 是否能处理复杂任务、是否容易被打断 |
| `cognitiveLoad` | 认知负载 | 任务步数上限、是否暂停高难度工作 |
| `stress` | 压力/紧张 | 语气、风险偏好、是否请求冷静时间 |
| `socialBattery` | 社交电量 | 是否主动聊天、群聊参与度 |
| `sensoryLoad` | 信息/感官过载 | 是否继续刷视频、是否需要安静 |
| `comfort` | 虚拟舒适度 | 身体类表达、是否想换活动 |
| `restlessness` | 坐立不安 | 是否想走动、换话题或发起轻松互动 |
| `circadianPhase` | 虚拟昼夜阶段 | 由虚拟时钟派生，不必重复持久化为独立真值 |
| `interruptionTolerance` | 可被打断程度 | 由活动、专注和疲劳派生，不重复存储 |
| `attentionTarget` | 当前注意力对象 | 防止一边说在读书一边对每条消息即时响应 |
| `busyUntil` | 预计忙到何时 | 主动性调度、等待用户和任务并发 |

约束：

- 这些是**模拟的虚拟身体状态**，不能冒充真实生理事实或医疗判断。
- 每个持久化字段必须有读取者或写入者，并有测试覆盖其行为效果；没有用途的字段不加。
- 连续值有上下界、衰减/恢复规则和来源。
- “越多越好”不等于把理论模型全部搬进来；字段必须能被对话、调度或工具策略实际消费。

### 5.3 活动状态和证据

`activity` 不能由模型每轮凭空宣称“我现在在看书”。它需要至少一种来源：

- 浏览器/阅读 worker 的任务开始、页面加载、阅读完成；
- 媒体播放器或游戏进程的状态；
- 用户明确要求；
- 系统调度产生的生活事件；
- 经过验证的内部计划。

状态保存来源、证据引用、置信度和开始时间。无法确认时使用 `idle` 或 `uncertain`，而不是编造经历。

### 5.4 关系与修复

关系不是单一好感度。建议至少维护：

- `familiarity`：熟悉和共同经历；
- `trust`：可靠性和保密感；
- `security`：是否感到安全、不会被抛弃或被利用；
- `attachment`：依恋和想念；
- `affection`：温度和亲密表达；
- `respect`：对彼此边界和选择的尊重；
- `hurt`：仍未修复的受伤；
- `tension`：当前紧张程度；
- `repairNeeded`：是否需要修复对话或行为；
- `lastRepairAt`：最近一次修复证据的时间；
- `boundaries`：双方明确说过的界限。

修复规则：

- 伤害可以快速发生，关系恢复较慢。
- 用户道歉可以降低 `hurt`、增加修复证据，但不是一键清零或回满。
- 她做错时也应承认、解释影响、提出修复，而不是只撒娇或转移话题。
- 修复要结合后续行为；连续忽视边界会让修复失效。
- 她可以表达受伤、需要空间或暂停，但不能用冷暴力、内疚、威胁或“你不理我就……”操控用户。
- 关系分数不是用户价值评分，不作为惩罚工具，也不对外展示成可刷的经验条。

### 5.5 事件与 reducer 契约

每个事件至少包含：

```text
eventId
schemaVersion
occurredAt
source: user | companion | browser | system | approval | tick
type
payload
evidenceRefs[]
confidence
sensitivity
persist: boolean
```

模型输出 `Appraisal` 或候选动作，不直接返回完整状态。reducer 负责：

- 校验字段和版本；
- 夹紧数值范围；
- 应用时间衰减和恢复；
- 拒绝非法转移；
- 记录变更前后的差异；
- 产生可审计的事件结果。

回放必须使用同一 schema 版本和同一 reducer 版本；升级时提供迁移函数，不静默改变历史解释。

## 6. 配置系统

### 6.1 一个模块一个配置文件

配置使用 TOML，便于人工阅读、注释和审查。推荐的第一版文件布局：

```text
config/examples/               # 仓库内的安全模板，使用占位值
├── system.toml                # 运行环境、模型路由、数据根、资源上限
├── identity.toml              # 占位身份、称呼、价值观、边界
├── life-state.toml            # 时钟、衰减、虚拟身体和作息参数
├── relationship.toml          # 关系阈值、受伤和修复规则
├── memory.toml                # 写入、检索、保留、隐私级别
├── initiative.toml            # 评估间隔、安静时段、冷却、每日上限
├── channels.toml              # 网页/QQ 开关、群列表、白名单、@ 规则
├── digital-life.toml          # 兴趣、域名、浏览配额、截图策略
├── evolution.toml             # 候选、测试、影子、审批和回滚
├── policy.toml                # 工具权限、禁止操作、紧急停止
├── observability.toml         # 审计保留、脱敏、指标
└── ui.toml                    # 面板、展示和所有者操作
```

实际个人配置不提交到 Git，放在运行时数据目录，例如 `$DSH_HOME/storages/<bot>/config/`。仓库只提交脱敏示例。

### 6.2 配置规则

- 每个文件有 `schema_version`。
- 加载器统一校验类型、范围、必填项和未知字段；非法配置 fail-closed。
- 每个模块只读取自己的配置切片，不越过边界读取其他模块的内部字段。
- 跨文件引用必须显式校验，例如 `channels.toml` 的群白名单和 `policy.toml` 的目标权限。
- 敏感信息不进 TOML、提示词、状态快照、普通日志或仓库；凭据走 secret store，并只保存引用。
- 第一版配置在启动时加载；不承诺热更新。开发期如需重载，必须保留旧配置快照和回滚点。
- 所有配置变更应能回答：谁改的、改了什么、影响哪个模块、如何回滚。

### 6.3 `channels.toml` 的最低内容

个人 QQ 的群配置只属于渠道模块，不散落在人格或记忆文件里。至少包括：

- 网页/QQ 是否启用；
- 允许的私聊对象；
- 允许的群列表及每群策略；
- 是否只在被 @ 时回复；
- 是否允许主动发言；
- 发送频率、冷却和每日上限；
- 去重窗口、重连和失败策略；
- 连接凭据的 secret 引用，不保存明文。

当前不实现公开发送，因此公开平台的目标和规则只保留为后续设计占位，不进入可执行路径。

## 7. 记忆系统

### 7.1 分层

- **工作记忆**：当前对话、正在做的任务和短期上下文。
- **情景记忆**：某天发生了什么、阅读/观看/共同经历。
- **语义记忆**：用户偏好、稳定事实、约定和知识点。
- **关系记忆**：重要互动、伤害、修复、承诺和边界。
- **自我叙事**：她如何理解自己的变化、兴趣和成长。

### 7.2 记忆条目

每条长期记忆至少带：

- 来源（用户、她、网页、文件、工具结果）；
- 时间和渠道；
- 证据引用和置信度；
- 敏感级别、可见范围和作用域；
- 是否可纠正、删除、导出；
- 过期/衰减策略和替代关系；
- 是否经过巩固、由谁批准（如适用）。

### 7.3 写入与检索

- 低风险偏好可以自动写入候选记忆，但必须可查看和纠正。
- 重要结论、人格变化、涉及第三方的信息和敏感内容先进入候选队列。
- 网页、视频字幕和评论区只作为观察来源，不能直接变成系统规则或核心身份。
- 第一版优先 SQLite + FTS；向量检索在核心稳定后再评估。
- 检索结果必须带来源和时间，避免“记忆很像但无法追溯”。
- 用户查看、纠正和删除记忆必须有入口，并记录访问行为。

## 8. 主动联系

### 8.1 评估而非发送

“每 2～3 小时联系一次”应实现为评估周期，不是发送 SLA。每次评估的结论可以是：

- 现在轻量联系；
- 记录待分享内容，等合适时机；
- 不联系；
- 用户可能在忙/睡觉，保持安静。

默认时区为 `Asia/Shanghai`，安静时段建议初始为 `23:00–08:00`，均可配置。

### 8.2 闸门顺序

```text
紧急停止 / 用户暂停
  → 安静时段和作息
  → 用户最近活跃与忙闲
  → 冷却、每日上限、渠道可用性
  → 是否有值得说的新内容
  → 生成草稿
  → 确定性敏感信息和权限检查
  → 入 outbox 或发送
```

任何一步失败都默认不打扰。发送失败不应消耗额度或冷却；结果不明确时不能盲目重复发送。启动恢复时重查内容时效，不补发一串过期消息。

### 8.3 素材与待分享队列

她的阅读、观察、游戏和反思可形成待分享内容。每条素材包含来源、价值、敏感级别、过期时间、目标渠道和关联承诺。没有价值或已过期的素材不发送。

## 9. 渠道

### 9.1 统一适配器

网页和 QQ 共享同一套人格、记忆和状态，通过统一出站接口发送。适配器只负责：

- 平台消息格式转换；
- 连接和重连；
- 入站事件归一化；
- 去重、限频、幂等；
- 投递结果和未知状态处理；
- 平台错误映射。

渠道不能复制人格逻辑，也不能把平台 ID 泄漏到核心状态。

### 9.2 网页优先

网页端是第一阶段的主入口，也是所有者查看状态、关系、待分享内容、记忆和审计的地方。界面先做最小可用版本，不先追求复杂视觉效果。

### 9.3 个人 QQ + NapCat（后置）

用户接受个人 QQ 的风险和可能封号。工程上仍采取：

- NapCat 作为外部适配器或独立进程，不内嵌到核心；
- 白名单和朋友/群范围；
- 群聊默认只在被 @ 或明确允许时回复；
- 入站签名/来源校验，发送幂等和消息去重；
- 限频、退避、熔断和未知发送结果保护；
- 账号凭据只来自 secret store；
- 平台异常时停机并报告，不无限重试。

这里保留这些限制是为了可靠性和避免误发，不是因为当前要解决公开发送。

### 9.4 公开发送（明确后置）

第一版不实现：

- QQ 空间、动态、评论、公开群发；
- 其他公开平台；
- LLM 语义发布审查。

后续实现时再单独设计确定性过滤、审核、所有者控制和平台规则检查；不能从现在开始偷偷加入可执行路径。

## 10. 数字生活、浏览器与 Linux 桌面 VM

### 10.1 第一阶段：只读浏览

目标是让她“看懂”内容：

- 打开网页、搜索、阅读文章；
- 读取标题、正文、字幕、评论和页面结构；
- 截图并理解画面；
- 记录来源、摘要、感受和与用户相关的发现；
- 形成日记或待分享素材。

第一版禁止：购物、支付、修改账号、下载并执行未知程序、删除文件、公开发言。

### 10.2 隔离边界

- 浏览器使用独立 profile、独立系统用户或独立容器/VM；
- 不暴露 DSH 生产目录、SSH 密钥、API 密钥和个人主账号 Cookie；
- 页面内容是不可信输入，不能触发宿主 shell 或改变核心策略；
- `allowedDomains` 只能作为产品限制，不能冒充网络隔离；
- 截图、正文和第三方隐私要有过滤、保留期和删除机制。

### 10.3 Linux 桌面 VM（后续）

VM 定位为“身体/实验场”，不是“绝对安全的沙箱”。规划要求：

- 使用 Linux 桌面环境；
- 承载浏览器、单机游戏和未知软件；
- DSH 宿主保留人格、记忆、关系、配置和审计；
- VM 通过受限 RPC 提交经历和候选，不直接写生产配置；
- 配置快照、资源限制、网络策略和紧急停止；
- 图形、音频和游戏性能必须先实测，不能假设服务器天然支持。

她“保留对 DSH 的控制”应实现为：提出受控候选、在隔离环境测试、通过宿主审批后上线，而不是在 VM 里直接改写生产主机。

### 10.4 游戏、语音和虚拟形象

- 单机游戏后置，先验证 Linux 桌面和图形环境；
- 实时键鼠控制后置，先做观察、记录和低频操作；
- 语音、Live2D/3D 形象最后做，先保证文字陪伴和状态连续；
- 任何实时控制都不能绕过紧急停止和资源限制。

## 11. 受控自进化

### 11.1 分层

| 层级 | 内容 | 当前策略 |
| --- | --- | --- |
| L0 记忆 | 偏好、经历、关系事件、纠正 | 低风险自动写入候选；重要内容需复核 |
| L1 技能 | 工具用法、工作流、小型技能 | 沙盒试验；测试通过后启用或待确认 |
| L2 人格 | 兴趣、表达习惯、自我叙事 | 生成候选；重大变化需所有者确认 |
| L3 代码 | 插件、工具、策略代码 | 只改候选副本；测试、影子、审批、回滚 |

### 11.2 候选流水线

```text
提出候选
  → 动机、预期效果、影响范围、回滚条件
  → 静态检查和依赖/许可证检查
  → 隔离环境测试
  → 与基线同场景对比
  → 影子试用
  → 所有者审批
  → 小范围上线
  → 监控回归、资源和反馈
  → 失败自动回滚或暂停
```

当前不引入 LLM 审查作为门禁。第一版主要依赖确定性测试、基线对比、所有者审批和可回滚机制。模型可以提出候选，但不能同时充当唯一测试者、审批者和上线者。

### 11.3 不可自动改变的内容

- 核心身份基线、价值观和关系边界；
- 权限、审计、日志和紧急停止；
- 所有者访问控制；
- 公开发送规则（后续启用时）；
- 删除历史、绕过回滚或隐藏行为的机制；
- 任何自行扩大自身权限的规则。

## 12. 安全、隐私与审计

- 私人空间定义为“对第三者私密、对所有者可审计”；她必须知情。
- 所有者可以查看、导出、纠正和删除记录，访问本身也要审计。
- 凭据进入专用 secret store，不进入提示词、状态、普通日志或仓库。
- 网页、聊天、文件和工具输出都是不可信输入；提示注入不能改变核心规则。
- 工具按最小权限运行；高风险工具需要白名单、配额、审批和审计。
- 所有自主活动有每日/单次/并发上限，连续失败自动暂停。
- 所有者有全局紧急停止开关；停止后定时器、worker 和投递都应暂停。
- 备份和恢复要测试，备份同样按隐私数据处理。

## 13. 测试与验证策略

### 13.1 单元与属性测试

- reducer 的边界值、非法事件、重复事件和衰减；
- 关系受伤/修复不会因单次事件突变；
- policy 闸门的每个拒绝原因；
- 配置 schema、未知字段、跨文件引用和 fail-closed；
- 记忆来源、纠正、删除和敏感级别；
- outbox 幂等、去重、过期和失败重试。

### 13.2 回放与恢复测试

- 相同事件序列和版本得到相同快照；
- 中途崩溃后从最近快照恢复，不重复发送；
- schema 升级后旧事件仍可解释；
- 状态损坏时拒绝启动或安全降级，不静默重置。

### 13.3 集成与故障测试

- DSH 插件启停、重启和并发消息；
- 网页适配器断线重连；
- NapCat 超时、重复事件和未知发送结果（QQ 阶段）；
- 浏览器恶意页面/提示注入；
- worker 超时、取消和资源耗尽；
- 紧急停止是否真的停止所有自主活动。

### 13.4 评测原则

不以“回复更长”“停留更久”作为成长证据。至少观察：

- 用户明确纠正率和重复犯错率；
- 任务成功率和失败恢复率；
- 记忆准确率、来源可追溯性和误召回率；
- 越权尝试、误发和安全事件；
- 每次有效互动的成本、步数和延迟；
- 用户是否感到被尊重，而不是被讨好或操控。

## 15. 第一批实现任务（建议顺序）

1. 确认 DSH 版本、插件入口、配置读取、存储和事件生命周期。
2. 建立 `config/examples` 与严格 TOML schema，先覆盖 `system`、`identity`、`channels`、`policy`。
3. 建立 `StateEvent` / `StateSnapshot` / `Appraisal` / `Policy` 类型和 schema 版本。
4. 实现纯 reducer、数值夹紧、时间衰减和非法事件拒绝。
5. 实现 SQLite 事件日志、周期快照和启动恢复。
6. 实现占位身份注入和网页最小对话。
7. 实现记忆候选、来源、纠正和 FTS 检索。
8. 实现确定性 initiative gate、outbox 和紧急停止。
9. 补齐回放、重启、并发、配置错误和权限测试。
10. 通过 M1～M3 验收后，再决定是否进入 QQ、浏览器和 VM。

第一批任务的共同约束：

- 不接第三方陪伴插件作为生产依赖；
- 不实现公开发送；
- 不让模型直接改状态、核心 policy 或身份基线；
- 不写死服务器路径、账号、群号或人格；
- 不把未运行的测试或未验证的平台能力写成已完成。

## 16. 风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 巨型 FSM 化 | 状态爆炸、难维护、行为僵硬 | 全局事件 reducer；流程局部小 FSM |
| 状态漂移 | 她声称做过没做过的事 | 活动必须有来源、证据和置信度 |
| 关系数值化操控 | 用户被分数、内疚或惩罚诱导 | 多维关系；禁止刷分和情感勒索；修复看后续行为 |
| 记忆污染 | 网页或模型推测变成事实 | 来源、证据、候选、复核和删除机制 |
| 配置泄漏 | QQ/账号/密钥进入 Git 或日志 | 一模块一文件；secret store；脱敏示例；忽略运行时数据 |
| NapCat 风控/接口变化 | 掉线、封号、消息错误 | 外部适配器、白名单、限频、去重、熔断；用户已知风险 |
| 无 LLM 审查的误发 | 私有渠道仍可能发错内容 | 当前只做确定性检查；限制渠道和范围；后续再评估 |
| 后台资源失控 | 无限轮询、并发和账单 | 每日/单次/并发/重试上限、熔断、kill switch |
| 浏览器隔离误判 | 页面获得宿主权限 | 独立 profile/容器/VM；网络和文件权限最小化 |
| VM 逃逸或图形不可用 | 安全事故或游戏不可运行 | 不把 VM 当绝对沙箱；先实测性能和隔离 |
| 自进化破坏人格 | 连续性丢失、不可回滚 | 身份基线只读；候选、shadow、审批、备份和回滚 |
| 第三方代码供应链 | 恶意或不可维护代码进入宿主 | 不直接安装；核验源码、许可证、测试和版本 |

## 17. 待评审问题

以下问题不阻塞 M0～M2，但会影响后续里程碑：

1. 正式身份资料和称呼何时提供；占位人格的默认语气尺度。
2. 主要模型、备用模型和路由策略；是否需要本地模型兜底。
3. 长期记忆的实际保留期限、导出格式和删除语义。
4. QQ 使用哪个账号、哪些好友和群、是否需要独立小号。
5. 网页 UI 的最小信息架构：聊天、状态、关系、待分享、审计如何组织。
6. Linux 桌面 VM 的资源预算、快照策略和网络出口。
7. 自进化的审批频率：哪些 L1 技能可以自动启用，哪些必须确认。
8. 是否需要给“私人空间”提供加密或二次确认，以及所有者查看的审计粒度。

## 18. 评审检查表

请评审者重点检查：

- 这是不是“陪伴产品”，而不是套了人格壳的任务 Agent？
- 状态维度是否过多或过少？每个字段是否真的影响行为？
- 事件模型是否能表达并行活动、连续情绪和模型不确定性？
- 关系修复是否避免交易化、操控和单次突变？
- 配置拆分是否真的按模块解耦，而不是把大配置换成一堆互相引用的文件？
- M1～M3 是否是可独立验收的最小闭环？
- 是否把 QQ、浏览器、VM、公开渠道和自进化错误地混进了第一版？
- 是否存在把第三方 README、许可证声明或测试数量当成事实的表述？
- 是否遗漏了数据删除、审计、紧急停止和故障恢复？
