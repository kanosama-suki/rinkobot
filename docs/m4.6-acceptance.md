## 2. P0：提醒与记忆边界

### 2.1 实现结果

- 新增 `src/core/memory/arbiter.ts`，在写入长期记忆前同时检查本轮 `memoryCandidates`、`reminderCandidates` 和用户原话。
- 仲裁只使用确定性规则、提醒动作词、时间词和文本重合度，不增加第二次 LLM 审查。
- 纯提醒动作不进入长期记忆；混合句只提取稳定事实。例如“我对花生过敏，明早提醒我吃药”只保留过敏事实，不保存提醒动作。
- 显式“记住这个”保留确定性兜底，但同样经过提醒仲裁；纯提醒仍不能变成长期记忆。
- 显式兜底统一经过敏感内容守卫。修复了发现的一个隐私缺口：用户说“记住”时，敏感内容原先可能直接成为 `active`；现在仍只能进入候选。
- `memory_decisions` 记录脱敏动作、原因代码、来源和对象 ID，不保存候选或用户正文；统一审计时间线新增 `memory.decision`。
- `memory.toml` 新增 `candidate_archive_days = 30`。
- 冷却只把超期的普通候选转为 `archived`；`active`、`permanent`、`explicitly_requested` 记录不会自动归档。
- `archived` 候选不参与召回，但所有者在“归档”筛选中可见并能恢复；恢复后重置冷却起点。
- 提醒送达保持 `delivered` 历史状态，不修改记忆；页面把提醒拆成“当前 / 历史”两组。

### 2.2 schema 迁移

- SQLite schema 从 v9 升到 v10。
- `memories` 增加 `explicitly_requested` 和 `candidate_since`，记忆 record schema 升到 2。
- 新增 `memory_decisions` 表及时间、对象索引。
- v9 历史记忆在同一事务中重建成新表并升级 canonical `record_json`；任何一条记录无法解析都会让迁移回滚，不带着混合 schema 启动。
- 新增 `storage-v10-migration` 测试，覆盖历史候选冷却资格和显式标记。

### 2.3 回归测试

以下定向测试全部通过：

- `reminder-only candidate is suppressed by the deterministic arbiter`
- `a mixed reminder keeps only the stable fact`
- `explicit remember cannot turn a pure reminder into long-term memory`
- `a mixed reminder persists only its allergy fact and keeps the reminder`
- `explicit stable fact persists while explicit reminder fallback is rejected`
- `sensitive explicit fallback still stays candidate and unsearchable`
- `reminder delivery leaves the linked memory unchanged`
- `expired candidates archive without recall and can be restored`
- `archived candidates are visible, excluded from recall, and restorable`
- `v9 memories migrate with explicit flag and cooling eligibility`

## 3. P1：模型发现

### 3.1 实现结果

- 新增 `POST /kanobot/api/settings/models/discover`，只读、不保存配置、不回显密钥或 secret 引用。
- Magpie / OpenAI-compatible 使用当前页面草稿请求 `/v1/models`。
- DSH 使用 `listProviders()` 和 `listModels(route)`，并受 10 秒发现超时约束。
- 新增共享 `src/core/chat/model-catalog.ts`；聊天启动检查、视觉能力检查和设置页发现使用同一份模型列表解析。
- 共用解析只接受明确的 `modalities.input` 图片声明；缺失时是“能力未知”，不会被猜成支持图片。
- 视觉模型列表分为“明确声明支持图片”和“能力未知（保存前必须测试）”；明确不支持图片的模型不进入视觉列表。
- 页面增加“获取模型”、provider/model 可点选卡片，同时保留精确模型名手填作为兜底。
- 发现请求复用现有 Base URL 规范化、私网/回环限制、DNS 前置检查、10 秒超时、禁止重定向和 1 MiB 响应上限。
- 401/403、超时、非法响应、过大响应和不可用端点均显式失败；错误不包含凭据。
- 发现结果不会绕过保存时的精确模型、输出上限、reasoning effort 或视觉能力测试。

### 3.2 自动化与真实发现

- `model-settings` 的 12 项定向测试通过，覆盖分组、未保存、不泄漏密钥、401、超时、畸形响应、DSH provider/model 和未知视觉能力仍需测试。
- `model-settings-http` 通过，验证未认证失败和 HTTP 接口不返回凭据。
- 隔离实例中点“获取模型”后，真实 Magpie 返回 20 个聊天模型；页面显示“聊天 20 个”，没有错误且未创建运行时配置。
- 同一实例只读发现视觉模型时，页面得到 20 个明确声明支持图片的条目；全程未保存设置。
- M4.6.1 用本地假模型目录复核卡片交互：20 个聊天模型首屏显示 8 个，按钮显示“显示其余 12 个模型”；展开后显示 20 个，点选会写入精确模型名，并在空值时辅助填入输出上限和 `low` 推理档。视觉发现显示 4 个明确支持图片和 4 个能力未知的模型。

## 4. P2：WebUI 滚动与审计渲染

### 4.1 实现结果

- 桌面端 `body` 不整体滚动，应用高度约束为一屏，`.app-shell` 自身也不随内容增长。
- 聊天消息区使用 `flex: 1 1 0`、`height: 0`、`min-height: 0` 和 `overflow-y: scroll`；滚动条槽位稳定，输入框保持在聊天面板内。
- 右侧当前页签是唯一面板滚动容器；状态、设置、主动性、记忆和审计共用这一容器，不再嵌套内部滚动。
- `<= 900px` 时页面可以在聊天面板和所有者面板之间滚动，但两个面板各自固定高度，聊天区和当前页签仍各自内部滚动，不会随消息或审计条目无限拉长。
- `390px` 宽度下页签为两列，页面无横向溢出，聊天输入框完整可见。
- 审计使用 `DocumentFragment` 一次插入；首屏 50 条，“显示更多”扩展到 100 条。

### 4.3 模型选择器修复

- 聊天模型和视觉模型从原生 `<select>` 改为可点选卡片；选中项有勾选状态，卡片显示模型 ID、输出上限、推理档和图片能力。
- 首屏最多显示 8 个模型，剩余数量通过“显示其余 N 个模型”展开，避免一次铺满设置页。
- “获取模型”和“重新获取模型”都复用只读发现接口；发现失败显式显示错误，不静默回退。
- 点击模型卡片只填写表单草稿，不保存配置；精确模型名输入框仍然保留，允许手动输入。
- 精确模型名为空时自动填写；输出上限为空时使用发现结果；推理档为空时优先使用 `low`，没有 `low` 时选择第一个非 `none` 档位。
- DSH provider 也使用卡片选择；点选 provider 后自动重新获取该 route 的模型，不再要求再点一次“获取模型”。
- 视觉模型分为“明确声明支持图片”和“图片能力未知”两组；未知能力仍必须在保存前通过图片能力测试。
- 所有模型 ID、provider 名称和元数据通过 `textContent`/DOM 节点渲染，不把服务端返回值拼进 `innerHTML`。
