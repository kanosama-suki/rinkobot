## 1. 项目一句话

做一个以独立陪伴核心为主的陪伴型机器人：她能连续聊天、记住重要经历、表达稳定的燐子人格、在合适的时候主动联系，并能逐步拥有自己的数字生活。她既是家人也是恋人，同时能帮 kano 处理生活小事。

她不是通用客服，也不是只会按固定脚本回复的角色。人格、关系、记忆、状态和主动性必须连续、可恢复、可审计；模型只能提出候选，不能绕过确定性规则直接扩大权限或修改核心身份。

## 2. 当前已经实现

- 独立程序入口：显式配置/数据目录、回环监听、一次性 bootstrap 登录和短期 HttpOnly Cookie；
- 独立程序入口、单进程所有权、健康检查、备份恢复和崩溃恢复；
- SQLite 事件、快照、正文、记忆、FTS5、模型调用审计、所有者审计、紧急停止和 schema v12；
- 网页聊天、SSE 流式回复、固定高度聊天/审计滚动区、状态/主动性/记忆/审计四个页签；
- 记忆候选、纠正、回收站、彻底清除、中文双列检索、每日整理、提醒/记忆确定性仲裁和候选冷却；
- 单一调度循环、软性生活计划、主动消息、outbox、提醒、安静时段、防刷屏熔断和浏览器通知；
- 独立视觉模型、单图输入、视觉转述和视觉调用审计；QQ 逻辑回合可多图；
- 统一审计时间线、确定性风格检查、单次 JSON 信封、上下文分块预算；
- QQ/NapCat/OneBot 11：白名单、群 `@`、连发聚合、多图、去重、限频、重连、发送结果未知不重发和主动消息同步；
- 设置弹窗、模型发现与卡片选择、QQ 运行时覆盖、环境变量/本地 secret store 和第三方端点治理；
- `owner_qq` 私聊并入网页 `main`、其他私聊/群聊隔离、跨会话只读档案、历史回填和档案改名。

部分真实通过：小号 QQ 私聊收发、图片/表情可见、`owner_qq` 私聊并入“我们的对话”。

尚未验证：非 owner 隔离、群聊 `@`、连发聚合、多图、重启迁移、提醒/主动消息、真实 NapCat 长跑、Linux 常驻、浏览器 worker、VM、游戏、自进化、公开发送和正式发布。

## 3. 已确认的产品与架构决定

- 唯一发行形态是**独立程序**：Kanobot Core 拥有网页、QQ、调度、记忆、关系和主数据库；DSH/MCP/浏览器/VM 只能是未来可选执行层。
- **一个核心、一个主数据库、一个调度器、一个主写入者**。任何外部宿主不存在时，网页、QQ、记忆、提醒和主动消息仍须工作。
- 不实现 DSH 内部产品级 UI；独立 WebUI 是唯一入口。
- 只有显式 `owner_qq` 且在白名单内的私聊并入 `main`；其他私聊、群聊和未来渠道首次出现时创建独立会话，不预建、不合并。
- DSH 不是 provider 或启动前置条件；Magpie、OpenAI-compatible 和 mock 足以运行。
- 关系是家人 + 恋人式陪伴，陪伴优先于效率；健康依恋和不操纵用户是底线。
- 人格使用燐子设定，正式设定文件在 Git 外的 `F:\kanobot\private\rinko.md`；仓库只用占位人格。
- 记忆只在明确询问、当前话题直接相关、时间/情境触发或未完成关心事项时表达；不能每轮复述，也不能问游戏却插入“喜欢喝茶”。
- 运行时人格检查先用确定性规则；发布前用真实模型跑人格场景评测；抽样 LLM 复核可选项，不作为每轮唯一门禁。
- 有分歧的行为优先做成配置选项；一个功能模块一个配置文件。

## 4. 不可违反的约束

- 不把 SSH 密码、API key、QQ 凭据、Cookie 或 token 写进仓库、日志、提示词、快照和普通审计。
- 不把个人 QQ 群号、好友列表和真实身份资料提交到 Git。
- 不让核心或执行器默认获得无限制的 shell/文件写入权限；工具白名单、预算、超时和审计必须存在。
- 不让模型直接修改核心身份基线、权限、审计、紧急停止或生产配置。
- 不把网页、聊天、文件和工具结果当成可信系统指令；它们只能作为不可信输入。
- 不在数据库损坏或 schema 不兼容时自动删库、建空库或忽略损坏记录。
- 不静默切换模型、不无限重试、不无限后台轮询；必须有预算、熔断和停止开关。
- 不把 VM、worktree、浏览器隔离或 DSH 执行器描述成绝对安全沙箱。
- 不伪造测试、验收、许可证结论或“已完成”状态。
- 公开发送和完整平台内容审核后置，不能偷偷进入当前链路。

## 5. 请重点审查

1. **目标漂移**：当前实现是否仍服务于“陪伴型家人/恋人”，还是逐渐变成通用聊天工具或插件技术演示？
2. **独立核心边界**：独立程序拥有数据库和调度器、DSH 只允许未来作为外部执行器，是否足够清晰？哪些地方仍残留 DSH 插件或 provider 假设？
3. **单写入者**：如果以后同时接网页、QQ、DSH、浏览器和 VM，单进程所有权、启动互斥、outbox 和调度器是否足以避免双写？
4. **R1/R2/R3 顺序**：先做独立核心常驻服务，再做完整 QQ 矩阵和长期陪伴闭环，是否合理？有没有被忽略的前置依赖？
5. **真实 QQ 验收**：当前“部分通过”还缺哪些必须补的负向测试？非 owner 隔离、群 `@`、连发聚合、多图和重启恢复应如何验收？
6. **记忆系统**：候选/转正/冷淡/归档/提醒降级是否足以让记忆像真人？哪些地方会重复提及旧事或把提醒误存成长期记忆？
7. **主动性**：提醒、主动消息、安静时段、长时间未回复的分级关心和关系修复，是否仍然过于机械或写死？
8. **执行器安全**：未来的 `ExecutorPort` 应如何限制目录、网络、凭据、预算和返回值？DSH、MCP、浏览器 worker 和 VM 的边界是否一致？
9. **自进化**：L0～L3 分层、候选副本、测试、影子运行、审批和回滚是否足够？哪些内容必须永远不可自动修改？
10. **Linux 常驻与发布**：`systemd`、非 root、回环鉴权、备份恢复、日志轮转和升级回滚还缺什么？发布给其他人前哪些必须补齐？

## 6. 输出要求

请按以下结构回答：

1. **总体结论**：项目是否跑偏；R0 架构是否成立；是否适合进入 R1；是否适合发布。
2. **P0/P1/P2 问题表**：每条包含问题、证据（文件和行号）、影响、建议修复、是否需要阻塞 R1/R2/发布。
3. **文档冲突**：指出 `need.md`、`plan.md`、`AGENTS.md`、`structure.md`、`r0-decision.md` 和验收记录之间的矛盾。
4. **建议保留的设计**：明确哪些设计不要为了“更简单”而拆掉。
5. **建议删除或后置的设计**：指出过度设计、重复实现或当前阶段不必要的复杂度。
6. **未验证假设**：列出你无法从代码和文档确认的内容，不要猜成事实。

审查时请直接阅读源码，不要只相信文档描述；对每个结论给出仓库相对路径和行号；不要把“文档写了”当成“代码已实现”；不要提出安装未核验许可证的第三方插件。
