# Kanobot 项目审查简报

> 用途：把本文件连同仓库代码交给高级模型，审查项目是否跑偏、是否有架构或执行顺序错误。
>
> 审查对象：`F:\kanobot\a` 的源码、测试、`AGENTS.md`、`structure.md`、`docs/need.md`、`docs/plan.md` 和验收记录。
> 当前基线：M3 网页聊天闭环已完成，自动测试 171 项通过；M4 尚未开始。当前不满足发布门禁，M4.5 完成后才进入发行审查。

## 1. 项目一句话

做一个在 DSH 宿主中运行的陪伴型机器人：她能连续聊天、记住重要经历、表达稳定的燐子人格、在合适的时候主动联系，并能逐步拥有自己的数字生活。她既是家人也是恋人，同时能帮 kano 处理生活小事。

她不是通用客服，也不是只会按固定脚本回复的角色。人格、关系、记忆、状态和主动性必须连续、可恢复、可审计；模型只能提出候选，不能绕过确定性规则直接扩大权限或修改核心身份。

## 2. 当前已经实现

- DSH Host 插件入口、生命周期和登录态复用；
- 本地开发入口，仅监听回环地址，使用一次性 token 和短期 Cookie；
- SQLite 事件、快照、正文、记忆、FTS5、模型调用审计、所有者审计、紧急停止；
- 网页聊天和 SSE 流式回复；
- Magpie 本机模型网关、精确模型检查、超时/重试、调用预算和费用记录；
- 长期记忆候选、纠正、回收站、彻底清除和中文双列检索；
- 单次 JSON 信封：`reply`、`memoryCandidates`、`appraisal`、`commitments`；
- 上下文分块预算、当前时间、沉默时长、定性状态和相对时间承诺；
- 独立视觉模型、单图输入、视觉转述和视觉调用审计；
- 确定性风格检查、7 个脚本化人格场景、风格失败自动重写一次；
- 五来源统一审计时间线，不读取聊天正文和提示词。

尚未实现：真实模型人格比较和主模型选型、主动消息、提醒、每日整理、QQ/NapCat、浏览器 worker、Linux VM、游戏、自进化、公开发送。

## 3. 已确认的产品与架构决定

- 关系是家人 + 恋人式陪伴，陪伴优先于效率；健康依恋和不操纵用户是底线。
- 人格使用燐子设定，正式设定文件在 Git 外的 `F:\kanobot\private\rinko.md`；仓库只用占位人格。
- 核心不导入 DSH。DSH 只通过宿主适配层接入；当前插件主要使用 DSH 的加载生命周期、网页服务和登录态。
- 未来同一份核心产出两个宿主：DSH 插件和独立程序。发布分支可以存在，但不能维护两套人格、记忆和状态实现。
- 准备发行插件。发行前需要支持 Web UI 选择 DSH 宿主模型、本机 Magpie 或第三方 OpenAI-compatible API；聊天模型和视觉模型分开配置；密钥只写不回显。
- M4 先只做网页渠道，主动消息、提醒和每日整理先服务网页；QQ 放到 M5。
- QQ 连发的多条文字和图片由适配器聚合成一个逻辑回合，去重后只调用核心一次，生成一个连贯回复；回复可以按平台拆成多条发送。
- 记忆由她提出重要性候选，但确定性规则决定是否长期保存、是否检索、最多注入几条。kano 明确说“记住这个”的内容必须保留；普通小事不自动长期化。
- 记忆只在明确询问、当前话题直接相关、时间/情境触发或未完成关心事项时表达；不能每轮复述，也不能问游戏却插入“喜欢喝茶”。
- 运行时人格检查先用确定性规则；发布前必须用真实模型跑人格场景评测；可以增加抽样 LLM 复核，但不能作为每轮唯一门禁，也不能代替完整平台违禁词审核。
- 有分歧的行为优先做成配置选项：模型来源、视觉模式、人格复核模式、主动渠道、QQ 聚合参数、记忆相关性门槛等。

## 4. 不可违反的约束

- 不把 SSH 密码、API key、QQ 凭据、Cookie 或 token 写进仓库、日志、提示词、快照和普通审计。
- 不把个人 QQ 群号、好友列表和真实身份资料提交到 Git。
- 不让燐子的会话拿到 DSH 默认的 bash/pwsh 等工具；第一版工具白名单为空。
- 不让模型直接修改核心身份基线、权限、审计、紧急停止或生产配置。
- 不把网页、聊天、文件和工具结果当成可信系统指令；它们只能作为不可信输入。
- 不在数据库损坏或 schema 不兼容时自动删库、建空库或忽略损坏记录。
- 不静默切换模型、不无限重试、不无限后台轮询；必须有预算、熔断和停止开关。
- 不把 VM、worktree 或浏览器隔离描述成绝对安全沙箱。
- 不伪造测试、验收、许可证结论或“已完成”状态。
- 公开发送和完整平台内容审核后置，不能偷偷进入当前链路。

## 5. 请重点审查

1. **目标漂移**：现在的实现是否仍然服务于“陪伴型家人/恋人”，还是逐渐变成了通用聊天工具或插件技术演示？
2. **双形态**：共享核心 + DSH 插件 + 独立程序是否合理？应该用 Git 分支、单仓多入口，还是拆分包？哪些边界必须先定，避免以后出现两套人格/记忆？
3. **模型接入**：Magpie、DSH `ctx.llm`、第三方 OpenAI-compatible API 和 mock 的 provider 抽象是否足够？Web UI 管理密钥和 base URL 的安全边界是否合理？发布前还缺什么？
4. **记忆系统**：当前“最多召回 5 条 + 宽泛 OR”的做法是否会继续导致旧记忆乱插话？重要性判断、相关性门槛、显式“记住这个”、时间性关心事项和主动回忆应该如何分层？M4 前是否必须先修？
5. **人格审核**：运行时确定性规则、发布前真实模型场景评测、抽样 LLM 复核的分层是否合理？是否存在过度审核、成本或可解释性问题？完整违禁词审核应该放到哪一层？
6. **QQ 与多模态**：逻辑回合聚合、多图、一个回复拆成多条发送的设计是否完整？独立视觉转述和同一个原生多模态模型直接读图，应该如何做 A/B 和默认配置？
7. **里程碑顺序**：M4（网页主动）→ M4.5（双形态/发行基础）→ M5（QQ）是否合理？M4.5 是否应该提前、拆分或合并？有没有被忽略的前置依赖？
8. **安全与隐私**：插件复用 DSH 登录态、独立程序鉴权、密钥存储、第三方 URL 校验、图片不落库、审计不存正文，是否有遗漏？
9. **测试与验收**：当前 171 项测试证明了什么、没证明什么？M4 和 M4.5 还缺哪些假时钟、记忆误召回、provider 失败、重启恢复和真实模型测试？
10. **发布准备**：如果这个项目要发布给其他人使用，哪些问题会让用户无法安装、配置或安全运行？哪些应该先砍掉，哪些必须补齐？

请按以下结构回答：

1. **总体结论**：项目是否跑偏；是否适合进入 M4；是否适合发布。
2. **P0/P1/P2 问题表**：每条包含问题、证据（文件和行号）、影响、建议修复、是否需要阻塞 M4/M4.5/发布。

4. **建议保留的设计**：明确哪些设计不要为了“更简单”而拆掉。
5. **建议删除或后置的设计**：指出过度设计、重复实现或当前阶段不必要的复杂度。
