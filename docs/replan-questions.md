# Rinkobot 重新规划问题与决定

> 状态：**已确认（2026-11-10）**。Q1 批准；Q2 不需要；Q3 保留；Q4 不必须。
> 本文保留问题背景和用户回答，不再是待确认清单；执行口径见
> [plan.md](plan.md) 和 [r0-decision.md](r0-decision.md)。
> 关联提议稿：[replan-architecture.md](replan-architecture.md)
> 原则：只列会改变架构的问题，不问按钮、配色或具体实现细节。

## Q1. 是否批准“独立核心 + 可选执行器”作为新方向？

用户回答：**可以，批准。**

具体含义：

- Rinkobot 独立程序拥有网页、QQ、调度、记忆、关系、状态、主动性和主数据库；
- DSH、MCP、浏览器 worker 和 VM 只是可选执行器/连接器；
- DSH 不存在时，核心聊天、提醒、记忆和 QQ 仍然工作；
- 只允许一个主写入者和一个调度器。

为什么需要确认：当前 `docs/plan.md` 仍把“DSH 插件 + 独立程序”写成双形态，
但没有明确谁拥有生命周期和主链路。这个决定会改变 M6 的定位和后续里程碑。

可选替代：

- 保留 DSH 作为首选主程序，只把独立程序当备用（不推荐）；
- 完全放弃 DSH，只做独立程序（可先按 A 落地，再把 DSH 留作未来执行器）。

## Q2. 首版是否需要 DSH 内部的 Rinkobot 产品级 UI？

用户回答：**不要。首版只做独立 WebUI，DSH 后续只作为可选执行器。**

需要确认的原因：

- 若首版要求 DSH 侧边栏/设置页可用，就必须继续维护 DSH slot、client bundle、
  Profile、tarball 和宿主升级兼容；
- 若不需要，M6.7 的 UI 可作为参考归档，首版把时间投入到独立核心、QQ 和
  主动性闭环；
- 以后仍可增加“只读观察/显式操作”的 DSH 客户端，但不能让它成为第二套业务
  后端或伪造 Session 列表。

## Q3. 是否继续保留“所有者 QQ 私聊与网页 `main` 共用同一主会话”？

用户回答：**保留 M5.2.1 的已确认规则。**

具体含义：

- 只有显式配置且在白名单内的 `owner_qq` 私聊并入 `main`；
- 其他私聊和群聊保持独立档案、独立记忆作用域；
- 不从白名单、昵称、最近活动或“唯一会话”自动推断所有者；
- 不让 QQ 外部 ID 冒充核心 Session/档案 ID。

为什么需要确认：如果改为完全隔离，owner 在 QQ 和网页之间会失去共享上下文；
如果改为全部合并，会破坏已确认的隐私和记忆边界。这个选择会影响 schema、
迁移和所有渠道的上下文装配。

补充决定：如果以后接入聊群或其他渠道，**按现有规则在首次出现时创建独立
会话**，不要求提前批量创建，也不得并入 `main`。同一平台的新私聊、新群聊
各自拥有独立档案和记忆作用域。

## Q4. 首版是否必须依赖 DSH 宿主模型？

用户回答：**不必须。** DSH 宿主模型保留为可选 provider；默认应能用独立配置的
OpenAI-compatible/Magpie/mock provider 运行。

具体含义：

- 核心启动不因 DSH 不存在或 `ctx.llm` 未注入而失败；
- 用户可以选择本机模型路由、第三方兼容接口或未来的 DSH 执行器模型；
- 换模型不改变人格、记忆、关系或数据库；
- 真实模型选型和能力比较仍按原计划后置，不用 Q4 提前决定具体厂商。

为什么需要确认：如果 DSH 模型是硬依赖，独立程序和可迁移性会被削弱；如果
不是，模型适配层和安装文档需要以独立 provider 为默认路径。
