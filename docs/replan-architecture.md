## 1. 一句话产品定位

Kanobot 是一个持续运行的陪伴型核心：同一个人格、记忆、关系、状态和主动性
跨网页、QQ 及未来语音/虚拟形象延续；外部模型、工具执行器、DSH、浏览器和
VM 都可以替换，不能成为她“作为一个人”的生命周期边界。

## 2. 为什么重新规划

重新规划不是因为 M6 的代码没有跑通，也不是认定 DSH 有平台故障。M6.7/M6.8
已经有真实 DSH UI、测试和隔离环境证据；问题是**产品宿主与陪伴产品的生命周期
不匹配**：

1. 原 `docs/plan.md` 的 M6 是“只读浏览器”，M7 才涉及 Linux VM 和游戏；
   M6 实际转为 DSH 原生 Session 集成，是路线变化，不是原计划自然延续。
2. M5.2.1 已经有正式独立程序、网页鉴权、QQ/NapCat 适配器、调度器、长期记忆、
   关系状态、主动性、提醒、SQLite schema v12 和备份；陪伴核心并不依赖 DSH
   才能存在。
3. M6 的 DSH-first 路线把主聊天、QQ、主动性、面板和设置都向 DSH Session、
   Profile、preset、provider 和插件装载机制靠拢，增加了用户理解和运行故障面。
4. DSH `0.2.1-rc.5` 没有公开的 assistant 主动追加接口。把“她会主动联系”
   作为产品核心，却把生命周期交给无法承载该动作的宿主管线，是架构错位。
5. 用户希望产品可迁移、可配置、模块解耦，并能自己玩电脑、读书、玩游戏。
   这些更适合“稳定核心 + 可替换执行层”，而不是“整个产品住进某个编码 Agent
   的 Session”。

因此本轮先冻结 M6/M6.7/M6.8 的默认架构地位，保留其证据和可复用部件，再决定
新的主线。

不可丢失的不是 DSH 适配代码，而是：

- 同一个人格基线和关系连续性；
- 同一个主数据库和单一写入语义；
- 记忆的证据、候选、回收站、清除和审计规则；
- 主动性与提醒的确定性闸门；
- QQ 的幂等、去重、聚合和 fail-closed；
- 所有者权限、秘密不泄露和可恢复备份；
- 网页作为第一优先入口的完整体验。

package 当前仍叫 `@kanobot/dsh-plugin`，`dsh.bundle.patch` 仍指向 DSH 插件，
这反映的是 M6 期间的发行包装偏向，不代表核心只能作为 DSH 插件存在。新方案
需要纠正的是发行叙事和包边界，而不是重写核心。

## 4. DSH 插件方案的真实收益、成本和失败点

### 4.1 真实收益

- 可直接使用 DSH 的宿主模型、登录态和工作区能力。
- 可复用 DSH 的 Agent 工具、文件/命令执行和未来的桌面/浏览器集成。
- 有原生侧边栏、设置页和 Session 标题等 UI slot，适合开发者观察和操作。
- DSH 的 bundle、client module 和公开 Session API 已经能完成真实的原生 UI
  集成；M6.7 已证明不是“完全做不到”。

### 4.2 成本

- 用户必须理解 DSH Home、Profile、preset、Session、provider、模型凭据、
  tarball 安装和宿主重启生效等概念。
- 同一份能力出现两套 UI、两套配置入口和两套生命周期；DSH 设置页、WebUI
  和 Host 启动报告需要持续保持同步。
- 主聊天和 Session 绑定后，DSH 升级、Session 创建、标题、归档、UI slot、
  HMR 和权限变化都会成为产品级风险。
- QQ、提醒和主动性若不进入 Session 就要维护两套路径；进入 Session 又要处理
  Session 创建竞态、durable 消息、流式片段和 owner 并发。
- 测试环境必须搭建隔离 DSH Home、Profile、mock provider、agent preset 和
  浏览器 CDP，验收复杂度显著高于独立服务。

### 4.3 已出现的失败点

以下事实来自 M6.7/M6.8 归档工作，不等同于“DSH 有 bug”；它们说明产品宿主
选择不匹配：

1. **权限和工具边界不再是产品自己的边界。** DSH Session 既是聊天容器，又是
   编码 Agent 工作区；Kanobot 需要自己掌握记忆、关系、提醒和安全策略，不能
   让 Session 生命周期成为权限根。
2. **native 模式抑制了旧 QQ 和旧主动性。** 为避免双写和错误 owner 作用域，
   M6 只能让 QQ 写入停用，并让 `autonomyScheduler = paused_native`。这不是
   陪伴产品可以长期接受的状态。
3. **没有公开的 assistant 主动投递。** DSH `0.2.1-rc.5` 的
   `followup()`、`steer()`、`inject()` 都产生 user-role 输入；低层
   `Session.append()` 不是受支持的主动消息接口。把 native 模式当作主动联系
   的唯一路径会直接卡死产品核心。
4. **Session 创建不是零成本事务。** `SessionController.create()` 可能返回
   与请求不同的 ID，`agent/created` 可能在 create 返回前触发。M6.8.0 的围栏
   证明可以在未知 Agent 上 fail-closed，并显式 attach 返回 ID，但这要求额外
   的创建围栏、持久化状态、stale 恢复和跨重启核对。
5. **消息级时间线没有公开 API。** DSH 的聊天视口和 `scrollToTurn()` 属于
   client 组件内部，不能通过插件公开接口安全跳转；只能做逐会话只读档案。
6. **标题、UI 和设置不是产品核心。** 标题服务可用且不进入模型上下文，
   但不应该成为关系连续性的依赖；右侧栏和设置页可以很好用，却不能证明
   QQ/主动性已经真正接入。
7. **UI 宿主限制会变成产品限制。** 例如 DSH 设置弹窗在 390px 下的双栏布局
   压缩了 Kanobot 内容；不能用改 DOM 或改 DSH 核心绕过。

### 4.4 结论

DSH 可以作为**可选的执行器和观察面板**，但不能作为：

- 唯一数据库写入者；
- 唯一后台调度器；
- 唯一聊天历史来源；
- 唯一模型入口；
- 产品生命周期的根。

## 5. 三种架构方案和对比

### A. 独立程序优先（standalone-first）

Kanobot Core 自己拥有网页、QQ、调度、记忆、状态、主动性和数据库。DSH 只是
可选工具执行器、浏览器/电脑操作后端或 MCP 适配器。用户运行普通服务即可，
不需要安装或理解 DSH。

### B. DSH 插件优先

当前 M6 的实际方向。Kanobot 的主聊天、状态展示和 Session 绑定以 DSH 为根，
QQ 和主动性必须适配 DSH Session；适合希望把 Kanobot 完全放进 DSH 工作区的
开发者，但不适合作为所有用户的默认产品。

### C. 混合架构

独立核心为主，DSH 作为可选插件/连接器；共享同一数据库契约，但只有一个主
写入者。执行器通过窄协议接收任务、返回观察和结果，不能直接改写人格、记忆、
关系或主动性。

| 维度 | A 独立程序优先 | B DSH 插件优先 | C 混合：独立核心 + 可选执行器 |
| --- | --- | --- | --- |
| 聊天连续性 | 强；核心拥有完整历史 | 受 DSH Session 和升级影响 | 强；主历史仍由核心拥有 |
| QQ/NapCat | 直接复用现有适配器 | 需把 QQ turn 映射进 Session | 直接复用；DSH 不参与主链路 |
| 主动性和提醒 | 独立调度器可持续运行 | 受 DSH 生命周期和投递 API 限制 | 独立调度器；执行器不调度 |
| 记忆和关系隔离 | 统一由核心治理 | DSH 与核心形成双边界 | 核心统一治理，执行器按最小权限取数 |
| 工具和电脑操作 | 需自建或接执行器 | DSH 现成但强耦合 | DSH/MCP/其他执行器可替换 |
| 自进化 | 核心治理，执行层隔离 | 受插件宿主和 Session 限制 | 核心治理，候选执行在隔离环境 |
| 部署难度 | 最低；普通服务 | 最高；需要 DSH 概念和 Profile | 默认低；只有启用执行器才增加复杂度 |
| 故障隔离 | 好；核心与执行器分开 | 差；插件在宿主内 | 好；执行器故障不影响聊天和记忆 |
| 可迁移性 | 好；Windows/Linux 可迁移 | 低；依赖 DSH 环境 | 好；核心可独立迁移 |
| 可读性和维护成本 | 中等；模块边界清晰 | 高；双 UI、双配置、双生命周期 | 中高；需要明确的执行器契约和单写入规则 |

## 6. 推荐方案及其边界

**推荐：以 A 作为默认交付，以 C 作为长期演进目标；不采用 B 作为主路线。**

具体边界：

1. **默认入口是独立程序。** `npm start`/Kanobot 服务启动后即可聊天、收 QQ、
   收提醒、跑主动性、读记忆；DSH 不存在也不影响这些能力。
2. **一个核心、一个主数据库、一个主写入者。** 生产环境只允许 Kanobot Core
   进程写入主库。DSH、MCP、浏览器 worker 和 VM 只能通过明确接口提交任务和
   观察，不能直接打开 SQLite 主库。
3. **一个调度器。** 主动联系、提醒、每日整理和重试都只在核心调度器内执行；
   执行器不能拥有第二个 tick、定时器或 outbox 写入路径。
4. **DSH 是可选执行器，不是陪伴核心。** 它可以接收受限的任务包，例如读写
   指定工作区文件、运行允许的命令、生成截图或浏览指定网页；返回值是不可信
   观察，由核心校验和记录。
5. **权限与隐私默认最小化。** 交给执行器的任务不默认包含 owner 私人记忆、
   关系状态、提醒正文或其他 Session 内容；需要时由服务端组装最小投影。
6. **网页是正式第一入口；QQ 是正式第二入口。** 未来语音和虚拟形象通过新的
   ChannelAdapter 接入，不改变核心模型。
7. **DSH UI 不是首版必需。** 如果以后保留 DSH 面板，它只能是可选观察/控制
   面，动作走 Kanobot 的鉴权 HTTP API，不把 DSH Session 当作唯一状态源。
8. **执行器结果不可信。** 浏览器页面、命令输出、截图和模型生成内容都要经过
   核心的 schema、policy、权限和审计检查。
9. **自进化由核心治理。** 候选代码、技能、人格变更和回滚策略都由核心持有；
   执行器只运行候选，不得自行扩大权限或改写核心数据库。

这不是“完全不需要 DSH”。DSH 仍然有真实价值：它是目前可用的模型、工具和
工作区宿主，也可以成为未来“电脑生活”的执行后端之一。但它是可替换部件，
不是产品本体。

## 7. 从 M5.2.1 到新方案的迁移路径

本轮只写路径，不实施。迁移原则是**保留核心，重排宿主优先级**，不是把 M5.2.1
重写成另一个项目。

### 7.1 冻结与基线

- 当前 `replan/m5-baseline` 指向 `973cd5d`，工作区干净时再开始任何实现。
- `archive/m6-dsh-f14f880-20261110` 只保存已提交的 M6.6；M6.7/M6.8 WIP
  保存在 stash 中，不合并到新基线。
- 不把 schema v17 wholesale 合并到 v12 基线；v13-v17 的迁移、绑定和
  DSH Session 语义需要逐项重新评审。

### 7.2 核心运行时边界

在不改变行为的前提下，把独立程序与 DSH 插件重复的装配收敛为一个
`CompanionRuntime`（名称待定）：

- 拥有加载后的配置、数据库、单写入者、所有 core service、调度器和 outbox；
- 只依赖 logger、clock 和可选 model provider 等宿主能力；
- `src/app` 与未来可选插件都只做宿主装配；
- 任何宿主都不能复制人格、记忆、关系或主动性逻辑。

### 7.3 通道边界

- `ChannelAdapter` 只负责平台格式、鉴权/白名单、幂等、聚合和投递结果；
- Web、QQ、语音和虚拟形象都把逻辑回合交给核心；
- `conversationId` 是档案键，`sessionKey` 是逻辑键，外部平台 ID 不能冒充
  核心会话 ID；
- 只有核心 scheduler 能决定主动消息和提醒是否发送。

### 7.4 执行器边界

后续增加 `ExecutorPort`，而不是直接把 DSH 的 Session 暴露给业务代码：

- 输入：受限任务、允许目录、允许工具、超时、预算、审计关联 ID；
- 输出：结构化观察、产物引用、退出状态、脱敏错误；
- 禁止：直接写主库、调用核心 scheduler、读取未授权记忆、更改人格文件；
- DSH、MCP 本地进程、浏览器 worker 和 VM 都是该端口的独立实现。

### 7.5 发行与部署

- 先把独立程序作为正式安装路径，启动参数、配置目录、数据目录、端口和
  备份恢复写清楚；
- 修正当前 package 的 DSH-first 叙事（名称和拆包可后续决定）；
- DSH 安装说明降为“可选连接器/执行器”，不是“运行 Kanobot 的前置条件”。

### 7.6 迁移步骤顺序

1. 用户批准“独立核心 + 可选执行器”的方向；
2. 在隔离环境复跑 M5.2.1 独立程序、网页、QQ mock、备份和恢复；
3. 只写运行时/通道/执行器边界设计，不动 schema；
4. 用现有测试证明行为不回归，再拆装配；
5. 先做独立程序的产品化，再接第一个可选执行器；
6. 最后才评估是否需要在 DSH 内部提供客户端面板。

| M6.8.0 创建围栏、返回 ID 不同、未知 Agent 不猜 owner | 参考 | 技术上有价值，但成本说明不应默认自动创建外部 Session |
| M6.8 的 owner QQ 显式绑定和 DSH ingress | 归档 | 依赖 DSH 主会话；新方案先在独立核心内打通 QQ |
| DSH 公开 API 证据文档 | 保留 | 版本相关事实、平台限制和升级风险需要留档 |
| `paused_native` 作为长期状态 | 废弃 | 它是双宿主冲突的临时安全阀，不是产品状态 |
| 通过 DOM/iframe/伪造 Session 行/低层 `Session.append()` 实现产品能力 | 禁止 | 不可移植、不可验证，且违反公开接口边界 |

归档分支和 stash 是这些工作的安全保存位置；是否保留某段实现，必须在新架构
决策后逐项评审，不能默认“已有代码就应该继续用”。

## 9. 新里程碑草案

编号从 R 开始，避免与已完成的 M1-M5.2.1 和探索性的 M6 混淆。原计划的
“只读浏览器”并入 R5；“Linux VM/游戏”并入 R5；“受控自进化”并入 R6。
本轮不进入任何新的实现阶段。

## 10. 近期最小可行步骤

得到用户批准后，建议按以下顺序做最小步骤，而不是立刻恢复 M6 代码：

1. 在 `replan/m5-baseline` 上确认独立程序可用：临时配置/数据、mock 模型、
   Web 登录、聊天、记忆、提醒、QQ mock 和备份恢复。
2. 写一份 `CompanionRuntime`/`ChannelAdapter`/`ExecutorPort` 的接口设计，
   明确谁拥有数据库、调度器、模型和 channel。
3. 盘点 `src/app/server.ts` 与 `src/plugin/index.ts` 的装配差异，列出可提取
   与必须保留宿主专属的部分；不先改 schema。
4. 增加通用边界测试：单写入者、重启恢复、非 owner 作用域、错误不泄露、
   执行器超时/拒绝、宿主不可用不影响网页聊天。
5. 把独立程序安装/启动/数据迁移写成面向用户的文档，DSH 只作为可选项列出。
6. 在 R1/R2 通过前，不恢复 native 主动投递、不启动 QQ→DSH Session、不安装
   测试 tarball 到正式 Profile。

## 11. 风险、平台阻塞和已确认事项

### 风险

- 真实 NapCat/QQ 账号和真实第三方模型仍未验证，不能把 mock 结果当成外部
  环境通过。
- M5.2.1 的长期主动性、每日整理和提醒仍缺一到两周的真实日常观察。
- 如果独立程序不常驻，网页关闭、电脑休眠或进程退出时，主动联系和提醒无法
  发送；这是部署语义，不能用“浏览器通知”冒充后台投递。
- v12 → 新 schema 的任何迁移都必须保留现有记录并 fail-closed；M6 的
  v13-v17 不能未经评审直接套用。
- 单写入者需要进程级所有权和启动互斥；否则 QQ、网页或执行器可能产生两套
  outbox、timers 或记忆写入。
- 执行器（尤其浏览器、VM、命令、自进化）需要工作目录、网络、凭据、资源和
  审计隔离；DSH 的现成能力不等于产品安全边界。
- DSH 升级可能改变 Session、slot、client loader、模型目录和权限模型；它只能
  影响可选执行器，不能影响核心聊天。

### 平台阻塞

- **DSH native 主动投递**：`0.2.1-rc.5` 没有受支持的公开 assistant 追加接口。
  如果未来要做 DSH 原生 UI 主动消息，这仍是平台阻塞；不能恢复旧 main 调度器
  并将其伪装成 assistant 消息。
- **DSH 已展示流式片段不可撤回**：风格检查或策略只能在展示后记录问题；
  不能把不可撤回的片段当作最终可审计正文。
- **DSH 消息级时间线跳转**：没有公开的消息聚焦/滚动 API；只读档案可以保留，
  但不能用 DOM 注入伪造跳转。
- **DSH Session 创建返回 ID 可能不同**：未知 Agent 必须 defer，拿到返回 ID
  后再显式 attach；这会增加状态机和恢复成本，不能默认用于所有 QQ 会话。

### 已确认

- Q1 批准：独立核心优先，DSH 作为可选执行器/连接器；
- Q2 不需要：首版不做 DSH 内部 Kanobot 产品级 UI；
- Q3 保留：`owner_qq` 私聊并入 `main`，其他私聊/群聊/新渠道按规则创建
  独立会话，不预建、不合并；
- Q4 不必须：DSH 宿主模型可选，独立 provider 必须足够运行。

详细回答和补充条件见 [replan-questions.md](replan-questions.md)；R0 决策和
真实验收边界见 [r0-decision.md](r0-decision.md)。
