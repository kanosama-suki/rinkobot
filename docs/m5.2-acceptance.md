## 2. 实现结果

### 2.1 所有者共享会话与渠道隔离

- `main` 是所有者的共享会话，不是所有消息的日志。网页“我们的对话”和显式所有者 QQ 私聊共享同一 `KanobotChatService`、上下文、长期记忆、提醒和关心候选。
- 新增 `qq.owner_qq` / 设置页 `ownerQqId`。所有者 QQ 必须显式填写且同时出现在 `private_allow`；未填写时所有 QQ 私聊都与网页隔离，不会用白名单第一个账号推断所有者。
- 只有指定所有者 QQ 的私聊映射到 `main`。其他私聊使用 `qq-private-<id>`，群聊使用 `qq-group-<id>`；它们共享全局模型预算，但使用独立 chat service，不注入所有者长期记忆，也不提交面向所有者的提醒/关心候选。
- QQ 回复只发送回当前 QQ 目标；网页普通回复不会自动推送到 QQ。“全部对话”只读汇总不会进入任何会话的模型上下文。
- 同一消息只按 source conversation 存储一次；档案查询不复制消息，也不改变 `main` 的历史。

### 2.2 网页双视图与分页

- 网页聊天增加“我们的对话 / 全部对话”两个视图。
- “我们的对话”对应 `main`，保留输入框和发送能力。
- “全部对话”是跨会话只读档案，支持来源筛选、日期分组和“加载更早的消息”；档案视图不显示 composer。
- 档案消息显示来源徽标：“我们的对话”“QQ 私聊 · <id>”“QQ 群 · <id>”。
- 历史默认每页 50 条，上限 100 条；游标使用 `messages.seq`，不依赖可能重复的时间戳。
- 新增或扩展接口：
  - `GET /kanobot/api/conversation?limit=50&beforeSeq=<seq>`
  - `GET /kanobot/api/conversations`
  - `GET /kanobot/api/timeline?limit=50&beforeSeq=<seq>&conversationId=<id>`
- `limit`、`beforeSeq` 或 `conversationId` 非法时显式返回 400，不会静默回退到默认值。

### 2.3 滚动与响应式布局

- 桌面端页面高度约束为一屏，聊天区和当前右侧页签各自只有唯一滚动容器。
- 聊天区使用 `min-height: 0`、`flex: 1` 和 `overflow-y: scroll`，输入框保持可见。
- 档案视图隐藏 composer 和对应提示；`.composer[hidden]` 的 `display: none` 能覆盖原有 `display: grid`。
- 移动端恢复文档流布局，聊天区和面板各自内部滚动；390px 宽度下没有横向溢出。
- 审计页签仍按 `DocumentFragment` 批量渲染，保持 M4.6 的首屏 50 条和“显示更多”边界。

### 2.4 图片与表情边界

- M5.2 不改变现有图片输入：网页基线仍是一张图，QQ 逻辑回合按现有配置最多逐张转述 4 张图。
- 图片不写入正文、事件、快照或记忆；视觉失败不会伪造描述或静默降级。
- 本轮不新增表情包/贴纸解析，也不新增原生多模态模型选择；这些能力仍待后续里程碑。

## 5. 缺陷与修复

- 浏览器验收发现档案视图的 composer 仍可见：`.composer { display: grid; }` 覆盖了原生 `hidden`。已补 `.composer[hidden]` 和 `.composer-hint[hidden]` 的 `display: none`，并增加 UI 回归断言。
- `chat-http.ts` 原先使用 `parseLimit(...) ?? 50`，会把非法 `limit` 与缺省值混为一谈并静默回落到 50。已拆分“缺省”和“非法”状态；非法值显式返回 400，并补 HTTP 测试。
- 未发现需要修复的 P0/P1 产品缺陷。
