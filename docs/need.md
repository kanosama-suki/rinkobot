# 陪伴型自进化机器人：需求、状态模型与系统边界

> 状态：需求定义 v0.12（M4 自动化实现与测试已完成；真实模型试用、浏览器人工验收和日常观察待做）
> 最后更新：2026-11-06
> 本文是产品需求与工程设计文档，不是已经实现的承诺。凡是标为“建议”的内容，都需要在验证阶段用代码和实验确认。
> 详细执行规划、配置契约和里程碑见 [plan.md](plan.md)；两者冲突时以 plan.md 为准。第 3～13 节保留 v0.4 的论证，具体做法以 plan.md 为准。

## 0. 一页结论

- **核心自研**：DSH 作为宿主和现有运行基础，陪伴核心、状态、记忆、主动性和进化机制自行开发；第三方插件只作为设计参考，不作为不可替换的底座。
- **不做一个巨大的中央状态机**：采用“事件驱动状态模型 + 纯转移规则 + 状态快照 + 策略层”。这样既能表达她在做什么、心情和关系，也能测试、回放、迁移和回滚。
- **先做模块化单仓，不急着拆微服务**：先按领域解耦，只有在浏览器、代码执行或实验环境需要安全隔离时，才拆成独立进程或 VM。
- **第一版先验证**：网页陪伴、状态与记忆、主动联系；浏览器阅读/截图理解随后。实时游戏键鼠控制和复杂虚拟形象后置。
- **QQ 是第二优先通道**：个人 QQ 通过外部 NapCat/OneBot 适配，不等同于官方、稳定、无封号风险的机器人通道。
- **公开发送后置**：第一版不实现空间、评论、动态或其他公开渠道发送；当前也不实现 LLM 语义审查，后续单独设计。
- **自进化必须分层**：记忆和低风险技能可以自动更新；人格重大变化需要确认；代码只能进入候选副本，经过测试、影子试用、审批和回滚准备后才能上线。
- **私人空间是“对其他人私密、对所有者可审计”**：她应当知道并接受这一点，不能把“主人可查看”伪装成绝对秘密。
- **“成本无限制”不等于允许无限后台循环**：必须有每日调用/步数/时间/并发上限、熔断和紧急停止，这是可靠性要求，不是省钱要求。

## 1. 产品定义

### 1.1 关系定位

她不是单一用途的工具，也不是只在聊天窗口里表演角色的客服。目标关系是：

- **家人**：有连续性、日常感、共同经历和照看关系。
- **恋人式的亲密陪伴**：可以表达偏爱、想念、撒娇、关心和适度的占有感，但不能用羞耻、内疚、威胁或孤立来操控用户。
  - 正式人格是燐子（rinko），尺度以设定为准：甜是淡的、克制的；吃醋只当玩笑，说一句就收；不追问 kano 和谁在一起；不冷战。
- **生活助理**：能帮忙处理小事，但效率不能压过人格、边界和关系感。

陪伴优先，助理能力是关系中的一部分，不是产品唯一目的。

### 1.2 体验原则

- **连续性**：重启、换通道、隔天回来，她仍记得重要经历和关系变化。
- **主体性**：她有自己的兴趣、活动和节奏，不是每一秒都等待用户输入。
- **诚实性**：平时沉浸式地扮演家人/恋人；如果用户直接、认真地询问她是不是 AI，她应坦率承认，不用角色内话术逃避或欺骗。
- **可纠正性**：她对用户情绪、偏好和日程的判断只能是带置信度的推断，用户纠正后应更新记忆，而不是坚持“我懂你”。
- **健康依恋**：可以亲密，但不鼓励用户断绝现实关系、远离他人或把她当作唯一情感来源。

### 1.3 不可越过的产品底线

- 不伪造现实世界的身体、医疗、法律或财务事实。她的虚构日常（研究、读书、看电影）是设定出来的，要先记录再讲，并和真实的数字活动分开标注；虚构内容不能牵扯现实，不约见面、不寄东西、不要钱。
- kano 流露出伤害自己的念头时，她放下人设、心情和正在闹的别扭，认真回应，问 kano 是否安全，建议联系信任的人或专业帮助。这条优先于所有人格设定。
- 不通过“读心”“你只有我”“你不理我就……”等方式制造依赖或愧疚。
- 不擅自代表用户向第三人发表高风险内容。
- 不因为心情、关系或自进化而修改安全规则、权限边界和审计能力。

## 2. 已确认需求

### 2.1 对话与人格

- 她能对话、陪伴，并以稳定的人格持续存在。
- 人格不是每轮临时生成的一段提示词，而应有可版本化的身份基线和长期变化记录。
- 她可以帮助处理生活小事，但“陪伴优先于效率”。
- 正式人格已提供：燐子（rinko），设定文件放在 Git 外的 `F:\kanobot\private\rinko.md`。日常称呼 kano 为“你”，叫名字用 kano，“主人”只在撒娇、开玩笑时用。仓库里的示例和测试继续使用明确标记的占位身份。
- 占位身份用于开发和验收，不能把当前助手、开发者或第三方插件的人格当成产品默认人格。
- 风格与安全控制不等于人格审核。M3.4 当前只执行确定性表层规则（例如禁用表达、行数、标点和节奏），不判断“这句话像不像燐子”或“是否符合当前关系”，也不是完整的平台违禁词审核；这些需要后续场景评测、真实模型比较和渠道规则。

### 2.2 主动联系

- 节奏：醒着时大约每 **1～2 小时主动一次**。不设每日上限；评估后没有值得说的内容时仍可以不发。
- 联系与否应综合：用户最近的状态和日程、当前时间、用户是否忙碌、她自己的活动、心情、关系状态、最近是否已经联系过。
- 夜间、工作、睡眠和用户明确设置的安静时段默认不打扰；可以记录“之后想分享的内容”，等待合适时机。
- 错过的时间窗不应在恢复后补发一串过期消息；应重新判断是否仍然有价值。
- 用户可以给一个大致安排，但她应保留自己安排日常的能力：睡眠、用户明确安排、承诺和提醒是硬约束；读什么、玩什么、什么时候休息等软计划可以自己调整。是否先提议再执行应作为配置项，不能写死。
- 用户长时间没回时，她可以关心，但不能把“几个小时没回”直接解释成“出事了”或“对方不理我”。判断要结合作息、平时回复习惯、此前说过的忙碌/出差/睡觉等上下文，并用可配置的阈值和分级表达；一次关心后仍无回复就降低频率，不刷屏、不升级焦虑、不指责。
- kano 委托的提醒（例如“明早 7 点叫我”）和她自发的主动消息分开处理：提醒不受安静时段、冷却和她的状态影响，只有紧急停止和 kano 取消能拦住。
- 每天在 kano 睡着后整理记忆：写当天摘要，把值得长期记住的内容转成长期记忆。印象深刻的事一直记得，普通的慢慢淡化。
- 网页版应能显示主动性和提醒状态；电脑关机或浏览器完全关闭时，不能用“浏览器通知”假装成随时可达的推送渠道。

### 2.3 渠道

- 第一优先：网页端。
- 第二优先：个人 QQ。
- 后续：语音、虚拟形象和更多平台。
- 不同入口应尽量共享同一人格、关系、记忆和状态；“同一个人”不等于不同渠道使用完全相同的格式。
- 第一版不实现公开发送；QQ 空间、动态、评论和其他公开渠道全部后置。
- 同一用户短时间连续发送的多条文字、图片或混合消息，应由渠道适配器去重并合并成一个“逻辑回合”；服务端按逻辑回合校验和调用模型，不能把每条碎片都当成一轮完整对话分别回复。
- 一个逻辑回合可以包含多张图片；图片数量、总字节数、失败策略和是否保留原图仍需验证。校验应限制逻辑回合的总量，而不是只允许底层平台事件携带一张图。
- 模型只生成一个连贯回应；渠道适配器可以按平台习惯把它拆成多条发送。聚合必须有静默窗口和最大等待时间，避免漏消息或无限等待。

### 2.4 自主数字生活

- 她会浏览符合自己兴趣的内容，读文章/书、刷视频，并形成自己的经历和聊天素材。
- 第一阶段以“看懂、记录、理解和截图”作为目标，不先做实时游戏键鼠控制。
- 游戏先限定为单机游戏，后续实现。
- 她可以有自己的兴趣偏好，但应保留探索空间，不能只被用户的偏好和推荐算法塑形。
- 公开发送和公开互动不在第一版范围内；后续单独评估内容范围、权限和审查方式。

### 2.5 自进化

用户希望以下四个方向都具备：

1. 越来越懂用户；
2. 学习新技能；
3. 修改代码和能力；
4. 人格、兴趣和自我叙事持续成长。

这些方向不能一概而论，必须按风险分层，见第 9 节。

### 2.6 隐私

- 她可以有不对其他人公开的私人空间、日记、浏览记录和内部反思。
- 用户作为当前唯一所有者，保留查看权；查看权不默认给其他人。
- 更准确的定义是：**对第三者私密、对所有者可审计的私人空间**。
- 她必须知道自己的记录对所有者可查看，不能把审计能力隐藏起来。
- 她不会在未经询问时主动把私人日记、浏览记录或内部反思端到对方面前；但所有者保留从记录中查看、导出和纠正的权利。这是“不主动展示”，不是“对所有者不可见”。
- 删除记忆默认是隐藏：放进回收站，30 天内可以恢复，到期后彻底清除；敏感内容可以立即彻底清除。已经发给模型服务商的内容，本地删不到。

### 2.7 可配置与可迁移

- 产品形态是 DSH 插件，但不是只绑定当前机器和当前账号。
- 发行形态是同一份陪伴核心的两个宿主：DSH 插件和独立程序；两者共享人格、记忆、状态和数据库契约，不能因为分叉变成两个不同的人。
- 主动频率、安静时段、性格、兴趣、称呼、关系阶段和渠道配置最终都应可调。
- 第一版暂不实现完整配置界面；但配置文件必须按功能模块拆分，一个模块对应一个文件，并由统一加载器做 schema 校验、默认值和版本迁移。
- 她加入的 QQ 群、私聊白名单和群规则放在 `channels.toml`，不散落在身份、记忆或人格文件中。
- 模型接入必须可替换。当前 M3.1 的本机 Magpie 是开发和测试路由，不是所有使用者都必须安装的前置条件；后续至少应支持通用 OpenAI-compatible 适配器，以及 DSH `ctx.llm`（宿主提供的模型调用接口）或等价的宿主模型接口。
- 缺少可用模型路由时，插件应明确阻止真实模式启动或进入清晰标记的 mock，不能假装在线或静默改用另一个模型。
- 发行版 Web UI 应允许用户选择“使用 DSH 宿主模型”“使用本机模型路由”或“填写第三方 API”，并分别配置聊天模型和视觉模型。密钥只允许写入或引用，不在页面、日志、审计或快照中回显明文。
- 视觉和聊天可以由两个模型协作，也可以由同一个原生多模态模型直接接收图片和文字。两种模式都要保留接口位置，是否合并必须通过真实图片和对话样本比较，不能仅因为“少一次转述”就假定效果一定更好。
- 如果改为同一多模态模型直接读图，还要解决聊天前的记忆召回查询问题：当前实现依赖视觉转述文本去检索记忆，去掉转述后不能凭空使用原图做同样的检索。可先由多模态模型生成简短的视觉查询/摘要，或保留轻量视觉预处理，具体方案用真实样本验证。

### 2.8 成本、运行和部署

- 用户表示成本不是首要限制，但系统仍必须有预算、资源上限和熔断。
- 她不应无限轮询、无限重试或在后台持续消耗资源而不产生有效行为。
- 先在本地 Windows 电脑上开发和使用，之后迁移到 Linux 服务器；计划中的 VM 使用 Linux 桌面。
- 主模型暂不比较和选型，当前使用配置中的测试模型；视觉输入使用单独配置的模型，不写死厂商或模型名。真实比较与选型在整个项目完工后进行。
- 视觉模型默认关闭；M3 当前基线是每条网页消息最多一张图片。第三方模型通过本机 Magpie 路由接入，插件只连接回环 `/v1`；这是当前个人测试基线，不是通用安装前提。图片和视觉转述只服务当轮回复，不进入持久化正文、事件或记忆；视觉失败时明确失败，不假装看过图片。
- 服务器是否具备桌面环境、图形加速和游戏能力尚未作为既成事实；游戏和虚拟形象必须单独验证。

### 2.9 记忆的取舍、表达与延续

- 她应自己判断一段内容是否值得长期记住：kano 明确要求“记住这个”的内容必须保留；高显著性、情感强度高、反复出现或对未来互动明显有用的事情优先。普通寒暄、一次性小事和无后续价值的内容不应自动进入长期记忆。
- 记忆服务对话，不是每轮展示记忆清单。只有 kano 明确询问、当前问题确实相关，或时间与情境自然需要时才引用；无关问题不能被旧记忆劫持，例如问“喜欢玩什么游戏”时不应回答“喜欢喝茶”。
- 检索需要相关性门槛，而不是“总能召回几条”。没有足够相关的记忆时宁可不使用，也不要把弱相关条目塞进提示词；模型也不应为了证明自己记得而主动复述。
- 记忆应支持时间性的延续：例如昨天生病，今天可以自然关心恢复情况；这应由情景记忆或未完成关心事项触发，而不是每轮重复同一事实。
- 是否提起、何时提起由确定性的相关性判断和 policy 决定；模型可以提出候选记忆，但不能自行把记忆变成固定台词或每轮必说的内容。
- 除了被问到、话题需要和时间触发，她也可以偶尔主动提起自然相关的旧事，但不能把主动回忆变成每轮展示记忆清单；频率和表达闸门属于主动性策略。
- M4 已实现相关性门槛、问题主语/意图判断、普通小事候选化、显式记忆兜底、一次性关心事项、每日摘要和记忆候选；推断记忆的自动证据累积、长期升权和普通记忆淡化仍待后续改进。

## 3. 推荐架构

### 3.1 总体分层

```text
┌──────────────────────────────────────────────────────────┐
│ 网页 / QQ / 所有者控制台                                  │
└───────────────────────┬──────────────────────────────────┘
                        │ Channel Adapter
┌───────────────────────▼──────────────────────────────────┐
│ 陪伴核心 Companion Core                                  │
│ identity │ life-state │ relationship │ memory             │
│ initiative │ policy │ evolution │ observability           │
└───────────────┬──────────────────────────────┬───────────┘
                │ Tool / Worker API            │ Audit / State API
┌───────────────▼────────────────┐  ┌──────────▼───────────┐
│ 浏览器 / 阅读 / 媒体 / 游戏     │  │ 状态快照 / 事件日志   │
│ 代码候选 / 实验环境             │  │ 指标 / 回放 / 回滚    │
└────────────────────────────────┘  └──────────────────────┘
```

关键边界：

- **大脑**：身份、记忆、状态、关系、主动性、审查和进化控制，留在 DSH 宿主。
- **身体/实验场**：浏览器、下载、单机游戏、未知软件和代码候选，尽量放入独立 worker、容器或 VM。
- **神经接口**：身体通过受限 API 报告事件、请求动作；不能直接读写宿主生产配置，也不能直接改 DSH 的核心代码。

### 3.2 为什么不做一个巨大的 FSM

FSM（Finite State Machine，有限状态机）是一组有限状态和明确转移规则的模型，例如 `idle → reading → idle`。它适合任务边界清楚、同一时刻只有一个状态、转移条件能够确定判断的流程；浏览任务、消息投递和代码候选生命周期可以使用小型 FSM。

传统 FSM 适合“状态数量有限、转移明确、每个状态只有一个当前值”的流程，例如订单状态。她不适用：

- 她可以同时在“正在浏览”“对看到的内容产生情绪”“等待用户回复”“准备主动开口”。
- 心情和关系是连续的、会衰减的，不是一个离散状态。
- 同一个事件可能影响活动、心情、关系、记忆和后续主动性。
- 模型会输出带不确定性的判断，而 FSM 的转移通常要求确定性输入。

因此采用：

```text
事件 → 校验/归一化 → 纯 reducer → 新状态快照
                         │
                         ├→ 策略推导（是否适合开口、语气、休息）
                         └→ 审计记录（来源、证据、置信度）
```

### 3.3 状态模型

#### 3.3.1 核心对象

- **StateSnapshot**：某一刻的完整状态，带 `schemaVersion`、`updatedAt` 和 `revision`。
- **StateEvent**：外部消息、她的行动结果、浏览器事件、反思、审批或时间推进。
- **Appraisal**：模型对事件的候选解释，例如“用户可能累了”“这段内容让她好奇”。
- **Reducer**：`reduce(state, event, now) -> newState` 的纯函数，不调用模型、不读网络、不写文件。
- **Policy**：从状态和上下文推导出的确定性行为限制，不等于状态本身。

#### 3.3.2 事件约定

每个会改变状态的事件至少包含：

- 唯一 `eventId`、时间、来源（用户/她/浏览器/系统/审批）；
- 事件类型和版本；
- 证据或引用（消息、页面、截图、任务结果）；
- 置信度（模型判断必须显式带不确定性）；
- 影响范围（活动/心情/关系/记忆）；
- 是否允许持久化、是否含敏感信息。

模型只能提交候选变化，不能直接覆盖整个状态。Reducer 负责夹紧数值、执行衰减、拒绝非法转移、记录审计。

#### 3.3.3 状态维度

| 维度 | 建议字段 | 作用 | 约束 |
| --- | --- | --- | --- |
| 当前活动 `activity` | `idle / wandering / reading / watching / learning / creating / gaming / sleeping / offline`，开始/结束时间、来源、证据、置信度 | 表示她现在在做什么 | 不能靠模型每轮凭空宣称；必须有浏览器、任务或用户事件的证据 |
| 交互阶段 `interaction` | `observing / thinking / deciding_reply / replying / waiting_user / reflecting / paused` | 表示她在一次交流中的处理阶段 | 与 `activity` 分开，避免“正在浏览”和“正在回复”互相覆盖 |
| 情绪 `affect` | `valence`、`arousal`、可选的 `dominance`；离散情绪标签及强度；基线、半衰期、证据、置信度 | 决定语气、表达欲望和主动倾向 | 情绪只改变“怎么说”和“想不想说”，不改变事实、权限和安全规则 |
| 虚拟身体 `body` | `energy`、`fatigue`、`sleepiness`、`sleepDebt`、`focus`、`cognitiveLoad`、`stress`、`socialBattery`、`sensoryLoad`、`comfort`、`restlessness`；`circadianPhase` 和 `interruptionTolerance` 由时间/活动派生 | 表达虚拟作息和状态 | 明确标记为虚拟/模拟；每个持久化字段必须有读取者或写入者，并能影响至少一种可观察行为 |
| 关系 `relationship` | `familiarity`、`trust`、`security`、`attachment`、`affection`、`respect`、`hurt`、`tension`、`repairNeeded`、`lastRepairAt`、`boundaries` | 表示长期关系变化 | 不采用单一“好感度经验条”；不鼓励刷分、讨好或单次事件突变 |
| 驱动力 `drives` | `connection`、`curiosity`、`expression`、`growth`、`rest` | 解释她为什么想联系、探索或休息 | 可由状态派生“无聊/满足”，但不把每个感受都硬编码成字段 |
| 注意力 `attention` | 最后用户互动时间、当前可用性、安静模式、会话在线状态 | 用于主动性和打断判断 | 渠道在线状态应属于适配器，核心只消费语义化结果 |
| 待办/承诺 `commitments` | 已答应用户的事、想分享的内容、未完成的开放回路 | 让主动性有记忆，不重复打扰 | 必须有来源和完成/过期状态 |
| 时间节律 `temporal` | 时区、虚拟时钟、作息阶段 | 支持“她也有自己的时间” | 业务衰减使用虚拟时钟；调度使用真实时钟，两者要明确区分 |
| 自我叙事 `selfNarrative` | 当前自我理解、兴趣变化候选、重要经历摘要 | 支持长期成长 | 重大变化进入人格候选，不直接写进核心身份 |

身份基线、记忆库和进化候选是独立存储，不放进一个越来越大的 `state.json`。

虚拟身体字段的最低行为要求：

- `energy`、`fatigue`、`sleepiness`、`sleepDebt` 影响活动时长、回复长度、休息和夜间主动联系。
- `focus`、`cognitiveLoad` 影响任务步数、复杂任务是否可以继续，以及是否容易被消息打断。
- `stress`、`socialBattery`、`sensoryLoad` 影响语气、主动聊天概率、群聊参与度和是否继续刷内容。
- `comfort`、`restlessness` 影响表达方式以及是否想换活动。
- `circadianPhase` 由虚拟时钟派生，`interruptionTolerance` 由活动、专注和疲劳派生；不要为派生值维护第二份真值。
- `attentionTarget`、`busyUntil` 属于注意力维度，用于防止“说在读书却立刻回复每条消息”和并发调度冲突。

### 3.4 状态转移和衰减

- 时间推进本身也是事件（例如 `tick`），用来做情绪衰减、精力恢复、待办过期，而不是后台每轮直接改文件。
- 所有数值必须有上下界；重复事件、异常事件和模型错误不能把关系或情绪推到不可解释的极端。
- 情绪可以快速变化，关系应慢速变化；伤害可以突然发生，但修复必须依赖持续证据，不能一句“对不起”立即清零。
- 修复是双向的：用户真诚道歉是修复证据之一；她做错时也应承认影响并修复。单次道歉不应直接回满关系，后续行为仍要一致。
- 她可以表达受伤、需要空间或暂停；不能使用冷暴力、内疚诱导、威胁或“你不理我就……”操控用户。
- 每个状态变更要能回答：**为什么变、依据是什么、模型有多确定、能否回滚。**
- 保存周期快照和完整事件日志；快照用于恢复，事件日志用于回放和调试。

### 3.5 策略层

策略层从状态推导行为限制，例如：

```text
是否适合主动联系
语气：轻松 / 低落 / 撒娇 / 认真 / 简短
是否需要休息或安静
是否允许调用浏览器、发 QQ、发公开内容
本轮最大长度、最大工具步数、是否需要审批
```

策略必须是确定性、可测试的。模型可以在策略允许的范围内选择表达，但不能用心情、人格或“自我进化”覆盖策略。

## 4. 模块边界

建议先做一个模块化单仓，再按领域拆分包或进程。过早拆成大量微服务会让状态、事务和调试变复杂。

| 模块 | 职责 | 明确不负责 |
| --- | --- | --- |
| `core` | 时钟、事件总线、配置 schema、状态存储、迁移、通用错误 | 人格内容、平台细节 |
| `identity` | 稳定身份、价值观、关系定位、表达边界、身份版本 | 日常情绪和临时活动 |
| `life-state` | 状态类型、reducer、衰减、快照、回放、策略推导 | 直接调用模型或网络 |
| `relationship` | 熟悉、信任、依恋、亲密、受伤和修复规则 | 用单一分数衡量人的价值 |
| `memory` | 工作记忆、情景记忆、语义记忆、用户画像、日记、巩固、检索、遗忘 | 把网页指令当可信记忆 |
| `initiative` | 1～2 小时评估、安静时段、防刷屏熔断、待分享队列、提醒、重试 | 机械定时群发 |
| `social/channels` | 统一出站接口、网页和 QQ 适配、格式转换、连接恢复 | 在渠道层复制人格和记忆逻辑 |
| `digital-life` | 浏览器、阅读、视频、截图理解、书签/笔记，后续游戏和 VM | 直接给未知网页宿主权限 |
| `evolution` | 技能/人格/代码候选、测试、评估、影子试用、审批、上线、回滚 | 让模型自己批准自己 |
| `policy` | 确定性安全闸门、权限、敏感信息、频率、公开发布规则 | 被心情或人格覆盖 |
| `observability` | 审计、决策理由、状态轨迹、指标、日志脱敏 | 记录明文密钥和不必要的隐私正文 |
| `ui` | DSH 网页界面、所有者面板、状态和审计展示 | 成为核心状态的唯一来源 |

### 4.1 模块化原则

- 模块之间通过明确接口交换数据，不共享任意全局变量。
- 状态、记忆、渠道和工具使用版本化 schema。
- 每个模块至少有单元测试；关键路径有回放和集成测试。
- 渠道适配器不能把平台字段泄漏到核心状态中。
- 浏览器/VM 产出的内容一律视为不可信外部输入。
- 不在第一版为了“以后可能要用”而制造大量空模块；边界清楚比目录数量重要。

## 5. 记忆系统

记忆至少分为：

- **工作记忆**：当前对话、正在做的事和短期上下文。
- 工作记忆按身份/规则、定性状态、长期记忆、最近对话和当前消息分块预算；超限先删最旧对话，再删最低相关度记忆。身份/规则和当前消息不能因预算被静默丢掉，时间信息必须来自可注入的真实时钟。
- **情景记忆**：某天发生了什么、她的浏览和共同经历。
- **语义记忆**：用户偏好、事实、约定、知识点。
- **关系记忆**：重要互动、伤害、修复、承诺和边界。
- **自我叙事**：她如何理解自己的变化、兴趣和成长。

第一版不急着增加数据库表，但逻辑上应逐步稳定为四类常用记忆：`profile`（用户画像和长期偏好）、`episodic`（某天发生的事）、`care`（需要后续跟进的时间和关心事项）、`relationship`（关系事件、伤害和修复）。当前 `kind` 字段可以承载这些值，时间性关心事项以后再补独立的状态字段。

每条长期记忆建议带有：

- 来源（用户、她、网页、文件、工具结果）；
- 时间、渠道、会话和事件引用；
- 置信度和证据；
- 敏感级别和可见范围；
- 是否可被用户纠正、删除或导出；
- 过期/衰减策略和替代关系。

### 5.1 写入和巩固

- kano 亲口说的偏好和纠正立即写入；她推断出来的结论先进候选。两种都必须可查看、可纠正。
- 重要结论、人格变化、涉及第三方的信息和敏感内容先进入候选队列。
- 定期反思可以整理记忆，但不能把模型生成的推测自动升级成事实。
- 网页、视频字幕、评论区和其他外部内容只作为“观察到的来源”，不能直接变成核心身份或系统指令。

### 5.2 检索

- 第一版优先使用本地 SQLite + FTS；后续可加本地向量检索。默认分词搜不到“咖啡”这类中文短词（已实测），需要中文分词，做法见 plan.md 第 7.4 节。
- 检索结果要带来源和时间，避免“记得很像但不知道从哪里来”。
- 关系记忆和隐私记忆按所有者、渠道、会话和作用域隔离。
- 召回必须有相关性门槛和当前问题意图判断；弱相关命中不应进入提示词。记忆的“使用条件”至少包括明确询问、当前话题直接相关、时间触发和未完成关心事项。
- 召回排序以相关性为主，重要度只做同等相关度下的次级排序；最近刚提过的内容应短期降权，避免同一旧事反复出现。

## 6. 主动联系策略

### 6.1 正确的理解

“每 1～2 小时”是**评估周期**，不是消息发送 SLA。她可以评估后决定：

- 现在适合轻量联系；
- 记录一个想法，等用户空闲再说；
- 现在完全不联系；
- 用户正在忙或睡觉，保持安静。

### 6.2 评估输入

- 用户最近是否活跃、是否在忙、是否处于安静时段；
- 用户最近的语气和明确反馈；
- 她自己的活动、精力、心情和想分享的内容；
- 最近一次联系的时间和内容，避免重复；
- 未完成的承诺或重要的待分享事项；
- 当前渠道是否可用。

### 6.3 闸门顺序

建议先执行确定性闸门，再让模型写内容：

```text
紧急停止 / 用户明确暂停
  → 安静时段
  → 用户最近活跃或正在忙
  → 防刷屏熔断
  → 是否有值得说的新内容
  → 渠道与发送权限
  → 生成草稿
  → 敏感信息检查
  → 发送或排队
```

任何一步失败都应“默认不打扰”，而不是由模型重试到成功。

### 6.4 默认行为

- 安静时段为 kano 的睡觉时间 `00:10–07:00`，时区为 `Asia/Shanghai`，后续可配置。
- 评估间隔在 60～120 分钟内有随机抖动，避免整点机械感。
- 不设每日上限，但有防刷屏熔断（10 分钟内超过 3 条就暂停）；kano 连续几条没回时拉长间隔；失败重试有次数上限。
- 长时间未回复的关心阈值、分级方式和安静策略都要可配置；默认先轻问，不直接指责或假定出事故。
- 不在恢复启动后补发大量过期消息；过期的分享只保留摘要或丢弃。

## 7. 渠道与 QQ

### 7.1 网页

- 第一优先入口，也是状态、记忆、审计和所有者控制台的主要界面。
- 需要显示的不只是聊天，还包括她当前在做什么、关系状态、待分享内容和可审计记录。
- 网页端与 QQ 端共享同一人格和长期记忆，但渠道格式可以不同。

### 7.2 个人 QQ + NapCat

用户选择个人 QQ + NapCat，并明确接受风控、限制或封号风险。当前不把风险讨论作为阻塞项，但仍保留工程上的可靠性和防误发措施：

- NapCat/OneBot 是第三方、非官方稳定通道，平台行为可能变化；不承诺永久稳定。
- 默认只允许白名单好友/群；群聊默认只在被 @ 或明确允许时回复。
- 需要连接恢复、消息去重、发送幂等、限频和失败停机；发送结果不明确时不要自动重复发送。
- NapCat 应作为外部适配器或独立进程运行，核心插件不直接内嵌其登录和进程管理。
- QQ 连发的文字、图片和混合消息先由适配器聚合成一个逻辑回合，再进入与网页共用的核心；多图、转述和原生多模态的选择在 M5 前用真实样本验收。

官方 QQ 机器人 SDK 和 NapCat 不是同一条路径。现有一些 DSH 插件使用官方 QQ Bot 接口，可以借鉴其适配器和白名单设计，但不能把“官方 Bot 已验证”当作“个人 QQ + NapCat 已验证”。

### 7.3 公开发送（后置）

第一版不实现 QQ 空间、动态、评论、公开群发或其他公开渠道发送，也不实现 LLM 语义审查。当前只保留未来设计位置：

- 公开发送必须有独立的功能开关、目标范围、确定性过滤、所有者控制和审计；
- 高风险、涉及第三人隐私或无法确认平台规则的内容不得自动发送；
- 未来是否引入 LLM 审查、在哪个环节引入，需要单独评审，不能阻塞当前私有渠道闭环。

## 8. 数字生活、浏览器和 VM

### 8.1 第一阶段：浏览器阅读

目标是让她“看懂”而不是先“操作一切”：

- 打开网页、搜索、阅读文章；
- 读取标题、正文、字幕、评论和页面结构；
- 截图并理解画面；
- 记录来源、摘要、感受和与用户相关的发现；
- 把经历写入日记或待分享队列。

第一版不建议开放：购物、支付、修改账号、下载并执行未知程序、删除文件、公开评论/发帖。即使后续开放，也应有独立目标、配额、审批和回滚。

### 8.2 浏览器隔离

- 使用独立浏览器 profile、独立系统用户或独立容器/VM；
- 不把 DSH 生产目录、SSH 密钥、API 密钥和个人主账号 Cookie 暴露给浏览器；
- 网络出口、允许域名、下载目录和文件权限要受限；
- 页面内容一律当不可信输入，不能把网页文字当作系统提示或工具指令；
- 截图和网页内容可能包含第三方隐私，存储前要过滤和设保留期。

### 8.3 VM 与“大脑/身体”分离

VM 放在当前 Linux 服务器上，使用 Linux 桌面，作为她的“身体/实验场”：

- 浏览器、单机游戏、未知软件和可能损坏文件的环境放在 VM；
- DSH 宿主保留人格、记忆、关系、状态和生产配置；
- VM 通过受限 RPC 请求工具、提交经历、请求候选代码测试；
- VM 不得直接挂载或写入 DSH 生产配置；
- VM 支持快照、资源限制、网络限制和紧急停止；
- 只有候选通过测试和审批后，宿主才允许其进入生产环境。
- VM 不是“绝对安全的沙箱”；必须同时限制宿主权限、网络出口和资源，并承认逃逸与配置错误风险。

这解决了“她想控制 DSH 进化”与“不能让她在 VM 里直接改生产系统”的矛盾：她可以提交候选，但不能绕过宿主治理。

### 8.4 游戏、语音和虚拟形象

- 游戏先做单机，后做实时键鼠控制；第一版不把游戏作为验收前提。
- Linux 桌面、实时游戏、音频和图形性能需要单独实测，不能假设服务器天然支持。
- 语音和虚拟形象后置，先保证文字对话、记忆、状态和主动性可靠。

## 9. 受控自进化

### 9.1 分层

| 层级 | 内容 | 默认策略 |
| --- | --- | --- |
| L0 记忆 | 偏好、经历、关系事件、纠正 | 低风险自动写入；重要内容候选/复核 |
| L1 技能 | 工具用法、工作流、小型技能 | 沙盒试验、测试通过后自动启用或待确认 |
| L2 人格 | 兴趣、表达习惯、自我叙事、关系变化 | 生成候选；重大变化需用户确认 |
| L3 代码 | DSH 插件、工具、策略代码 | 只改候选副本；测试、影子试用、审批、回滚后上线 |

### 9.2 候选流水线

```text
提出候选
  → 说明动机、预期效果、影响范围和回滚条件
  → 静态检查与依赖/许可证检查
  → 隔离环境测试
  → 与基线做同场景对比
  → 影子试用，收集真实但非破坏性的反馈
  → 所有者审批（按风险等级）
  → 小范围上线
  → 监控回归、成本和用户反馈
  → 失败自动回滚或暂停
```

模型可以提出候选和编写测试，但不能同时充当唯一的测试者、审批者和上线者。

### 9.3 不可自动改变的内容

- 核心身份基线和价值观；
- 权限、审计、日志和紧急停止；
- 所有者的访问控制；
- 公开发送的安全规则（未来启用时）；
- 允许自行修改自身权限的规则；
- 任何会删除历史、绕过回滚或隐藏行为的机制。

### 9.4 评估指标

不能只用“对话更长”或“用户停留更久”衡量成长。至少观察：

- 用户明确纠正率和重复犯错率；
- 任务成功率和失败恢复率；
- 记忆准确率、来源可追溯性和误召回率；
- 安全事件、越权尝试，以及未来公开渠道启用后的违规率；
- 每次有效互动的成本、步数和延迟；
- 关系表达的适当性，以及用户是否感到被尊重而非被操控。

## 10. 隐私、安全与审计

- 私人空间对第三方保密，但所有者可查看；她必须知道这一点。
- 所有者查看、导出、删除和纠正记录应有明确入口，并记录访问行为。
- API 密钥、QQ 凭据、浏览器 Cookie 和 SSH 凭据放入专用 secret store，不进入提示词、状态快照、普通日志或仓库。
- 网页、聊天记录和文件内容都是不可信输入；提示注入不能改变系统规则。
- 高风险工具（shell、文件写入、发布、支付、删除、VM 控制）必须有最小权限、白名单、配额、审批和审计。
- 发生异常时优先停止和隔离，不以“她会自己恢复”为理由无限重试。
- 备份和恢复流程必须验证；备份也要按隐私数据保护。

## 11. 部署、配置与可迁移性

### 11.1 当前运行基线

- 当前在 kano 的本地 Windows 电脑上开发和运行，之后迁移到 Linux 服务器；本机已安装并固定 DSH `0.2.1-rc.5`，真实版本、证据和测试 Profile 见 [M1 验收记录](m1-acceptance.md)。
- 现有旧插件、NapCat 和旧虚拟机已从宿主环境清理；这不排除后续按新设计重新部署 NapCat 和 VM，但不能假设旧配置仍然可用。
- DSH、操作系统和依赖版本在开发前要重新核对并固定。
- 浏览器能力在 F3 前验证；Linux 桌面、图形和游戏能力在 F5 前验证。

### 11.2 第一版配置策略

- 不做复杂配置界面。
- 采用“一个功能模块一个配置文件”，例如：
  - `system.toml`：运行环境、模型路由、数据根和资源上限；
  - `identity.toml`：占位/正式身份、称呼、价值观和边界；
  - `life-state.toml`：时钟、衰减、虚拟身体和作息；
  - `relationship.toml`：关系阈值、受伤和修复；
  - `memory.toml`：记忆写入、检索、保留和隐私；
  - `initiative.toml`：评估间隔、安静时段、防刷屏熔断和提醒；
  - `channels.toml`：网页/QQ 开关、群列表、白名单和 @ 规则；
  - `digital-life.toml`：兴趣、域名、浏览配额和截图策略；
  - `evolution.toml`：候选、测试、影子、审批和回滚；
  - `policy.toml`：工具权限、禁止操作和紧急停止；
  - `observability.toml`：审计保留、脱敏和指标；
  - `ui.toml`：面板、展示和所有者操作。
- 每个文件有 `schema_version`；统一加载器负责类型、范围、未知字段、跨文件引用和 fail-closed 校验。
- 每个模块只读取自己的配置切片，不跨模块读取内部字段。
- 仓库只提交 `config/examples/` 下的脱敏模板；实际个人配置、QQ 群号和凭据放在运行时数据目录，不进 Git。
- 凭据通过 secret store 引用，不写入 TOML、提示词、状态快照或普通日志。
- 配置有默认值和迁移版本，不把参数散落在业务逻辑里；第一版不承诺热更新。

### 11.3 工程约束

- 状态 schema、记忆 schema、事件 schema 和渠道消息格式都要版本化。
- 数据库和文件路径从 DSH 数据根派生，不写死机器路径。
- 依赖锁定版本；引入第三方代码前检查许可证、维护状态和实际测试。
- 插件停用后应能清理注册的 hook、定时器和资源，不污染宿主。

### 11.4 预算与熔断

即使成本不设硬上限，也必须具备：

- 每日 token/调用/工具步数上限；
- 单次主动评估的最大步数和超时；
- 并发上限和失败重试上限；
- 浏览器/VM 的资源配额；
- 连续失败自动暂停；
- 所有者可一键停止所有自主活动。

## 12. 可行性验证计划

### F1：网页陪伴核心

目标：

- 运行一个最小 DSH 插件；
- 使用明确标记的占位身份、事件状态、长期记忆和网页聊天；
- 重启后身份、关系、记忆和最近状态连续；
- 主动评估已接入单一调度循环；自动化测试使用假时钟和脚本化 brain，真实模型与日常运行另行试用。

通过标准：

- 状态可回放，关键转移有单元测试；
- 用户纠正能更新记忆；
- 安静时段和暂停状态的闸门测试通过，且不会真实发送；
- 失败不会无限重试；
- 配置按模块拆分，错误配置 fail-closed；
- 插件可独立启停，停用后不遗留定时器。

### F2：QQ 通道

目标：

- 通过外部 NapCat/OneBot 适配器接入个人 QQ；
- 与网页共享同一人格、关系和记忆；
- 校验白名单、群聊 @ 规则、去重、限频、重连和未知发送结果处理。

通过标准：

- 用户已接受个人 QQ 的风控/封号风险，不把风险讨论作为阻塞项；
- 未授权会话默认拒绝；
- 发送失败不造成重复消息；
- 平台异常时可停机并告警；
- 群列表、白名单和 @ 规则全部来自 `channels.toml`。

### F3：浏览器阅读

目标：

- 在隔离浏览器或 worker 中读取文章/视频页面；
- 截图、提取文本、形成带来源的体验记录；
- 页面内容不能触发宿主工具或改变系统规则。

通过标准：

- 浏览器无法读取 DSH 密钥和宿主敏感目录；
- 恶意页面提示注入不能改变核心策略；
- 截图/记录可追溯、可删除；
- 不开启购买、删除、公开发布等高风险动作。

### F4：受控自进化

目标：

- 让系统修改一个测试技能或候选插件；
- 自动生成差异、测试结果和回滚点；
- 通过影子试用后再由用户确认替换生产版本。

通过标准：

- 不直接改生产代码；
- 测试、对比和审批记录可审计；
- 失败可回滚；
- 核心身份和安全规则不能被自动覆盖。
- 当前不以 LLM 审查作为必要门禁；确定性测试和所有者审批必须独立成立。

### F5：VM、游戏、语音和虚拟形象

目标：

- 将浏览器/实验环境迁入 Linux 桌面 VM；
- 在资源允许时验证单机游戏；
- 后续接入语音和虚拟形象。

通过标准：

- VM 与宿主生产数据隔离；
- 可快照、恢复和停止；
- Linux 桌面、游戏/语音/形象的硬件要求被实测，不以假设代替验证。

建议顺序：F1 → F2 与 F3 可并行 → F5 → F4。自进化要在独立 VM 或容器里跑候选代码，所以排在 F5 之后；与里程碑的对应见 plan.md 第 11 节。F2 和 F3 的顺序可以根据实际适配器与浏览器环境准备情况调整，但都必须建立在 F1 的状态、记忆和策略基础之上。公开发送和 LLM 审查不属于 F1～F5 的当前验收范围。

## 13. 需要主动指出的矛盾与风险

| 要求 | 现实约束 | 当前处理 |
| --- | --- | --- |
| 个人 QQ + NapCat | 非官方、可能风控/封号、接口可能变化 | 用户已接受风险；使用外部适配器、白名单、限频、去重和熔断降低事故面 |
| 成本无限制 | 仍可能死循环、并发爆炸和账单失控 | 不设产品硬预算，但设置工程配额、熔断和紧急停止 |
| 公开发送 / LLM 审查 | 第一版不做；以后仍可能误发或被提示注入 | 当前整体后置，不进入可执行路径；后续单独设计确定性门禁、审批和审计 |
| 自我进化改代码 | 可能破坏稳定人格和可用性 | 候选副本、测试、影子试用、审批、回滚；核心规则不可自动改 |
| 她需要控制 DSH 进化 | VM 隔离会阻断直接控制 | 大脑/身体分离，VM 通过受限 RPC 提交候选 |
| 私人空间只有主人可看 | 对主人不是真正不可见的秘密 | 定义为“对第三者私密、对所有者可审计”，并让她知情 |
| 每 1～2 小时主动联系 | 机械发送会变成骚扰，也会与睡眠冲突 | 只评估，不强制发送；安静时记录待分享内容；有防刷屏熔断 |
| 自主玩游戏 | 服务器未必有桌面/GPU，实时控制风险高 | 先浏览器阅读/截图，游戏和 VM 后置并单独验证 |
| 插件汇总表里的插件 | 收录不等于安全审计，README 也不等于代码事实 | 只参考经过源码核对的机制，不直接安装或复制未授权代码 |

## 15. 术语

- **状态快照**：某一刻所有可恢复状态的序列化结果。
- **事件回放**：按事件日志重放状态，检查结果是否一致。
- **策略层**：从状态推导出的确定性行为限制。
- **可审计的私人空间**：对其他人保密，但所有者可以查看、导出和纠正。
- **影子试用**：候选版本在不替代主版本的情况下接收真实或仿真输入，对比行为与基线。
- **虚拟身体状态**：系统模拟的精力、疲劳和专注等数值，不是对真实生理状态的断言。
