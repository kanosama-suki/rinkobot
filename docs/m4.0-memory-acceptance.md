# M4.0 记忆质量门控验收

> 日期：2026-11-06
> 基线：`8b4c69c3892e`（M3 网页聊天闭环）
> 状态：M4 的第 0 步完成；M4 整体尚未完成。
> 插件版本：`0.12.0`；SQLite schema 保持 v8。

## 1. 目标

解决 M3 遗留的记忆质量问题：

- 弱相关旧记忆不能因为标成 permanent 就进入提示词；
- 问燐子自己的偏好时，不能用 kano 的偏好代替回答；
- 普通寒暄和一次性小事不能仅因来自用户就自动长期化；
- 明确“记住这个”必须有确定性保障；
- 同一旧事不能在短时间内反复被强调。

## 2. 实现

### 2.1 写入

- 普通 `user_stated` 内容默认进入候选。
- 明确“记住 / 记一下 / 记着”的内容直接 active，并在模型只给 `normal` 时至少提升为 `important`。
- 敏感和第三人内容仍先进入候选，不会因为显式记住绕过隐私门禁。
- 模型漏输出候选时，聊天链路会从短而直接的指令中提取内容并保存；复杂表达仍交给模型。

### 2.2 召回

- 先分析问题意图、主语和主题词。
- 问“你喜欢……”时默认不注入 kano 的 `user_stated` 偏好；共享经历、关系事件和关心事项仍可相关。
- 主题覆盖率低于 `memory.recall.min_relevance` 时返回空，而不是凑满条数。
- 同等相关度下按重要度排序；刚被召回的条目靠后，降低重复复述。
- 只有最终进入提示词的记忆才更新 `lastRecalledAt`。

### 2.3 配置

`memory.toml` 新增：

```toml
[recall]
min_relevance = 0.5
candidate_limit = 24
```

- `min_relevance` 范围 `0..1`，默认 `0.5`。
- `candidate_limit` 范围 `1..50`，默认 `24`，限制每类 FTS 查询先取多少候选。
- 不需要数据库迁移，schema 仍为 v8。

### 2.4 提示词

长期记忆块明确要求：

- 只在当前问题确实需要、话题直接相关或自然承接时使用；
- 不为了证明记得而每轮复述；
- 不主动展示记忆清单；
- 问燐子自己的偏好时，不用 kano 的偏好代替回答。

## 4. 边界

- 自动测试不调用真实模型，不证明真实模型一定会自然使用记忆。
- 当前相关性判断是规则和主题覆盖率，不包含 embedding 或知识图谱。
- “昨天生病、今天关心一次”的时间性关心事项属于 M4 后续的生活事件和主动消息步骤，本次只完成了记忆检索侧的防误召回。
- 普通候选的长期转正、重复出现升权和每日淡化仍要等每日整理实现。
