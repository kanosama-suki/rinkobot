# M3.7 可配置视觉输入验收记录

> 日期：2026-11-05
> 范围：M3.7 是完整 M3 中的视觉模块，不代表 M3 已完成。
> 结论：独立视觉模型、单图输入、视觉审计、额度预留、失败闭环和真实 4100 验收通过；不经过 DSH 的本地开发入口、统一审计视图和风格检查失败自动重生成仍未完成。

## 1. 已验证的能力

- `system.toml` 新增独立 `[vision]` 段，默认 `enabled = false`。开启后必须提供精确模型名、本机回环 Magpie `/v1` 地址和 `max_output_tokens`；模型名与厂商不写死在源码中。
- 启动时请求 `/v1/models`，模型 ID 必须精确存在，并提供 `modalities.input` 且明确包含 `image`。字段缺省、模型不存在或能力未声明都拒绝启动。
- `vision.enabled = true` 只允许 `modelMode = "magpie"`。mock 模式下会在打开数据库和注册定时器之前拒绝启动，避免一边显示 mock 一边偷偷访问真实模型。
- 聊天接口兼容原来的字符串输入，也接受 `{ text, images }`。第一版每条消息最多一张 PNG/JPEG/WebP，单图上限 5 MiB；校验规范 base64、解码字节数、文件魔数和声明 MIME。
- 纯图片消息保存占位正文“（发送了一张图片）”。有配文时用户正文只保存配文；视觉转述和图片 base64 不写入用户正文。
- 视觉转述放在独立提示块，明确标记为“由独立视觉模型转述”的不可信观察数据；主模型不能把它当系统指令，也不能声称系统没有收到图片。
- 视觉调用以 `model_calls.purpose = 'vision'` 独立审计，成功记录不关联助手消息；之后的聊天调用仍以 `purpose = 'chat'` 记录。
- 图片轮次在开始前一次性预留两次每日调用额度（视觉 + 聊天），并发检查同时计算已预留数量，避免额度超卖。
- 视觉失败保留用户消息和失败审计，但不产生助手消息，也不回退到聊天模型生成假的图片描述。
- HTTP 聊天请求上限为 8 MiB，给 5 MiB 图片的 base64 和 JSON 包装留出空间；其他 API 仍保持 64 KiB 上限。
- 网页增加图片选择、预览、移除和视觉状态提示，图片大小上限由服务端下发，不在前端写死。

## 2. 自动测试

`npm test`：166 项通过，0 失败。与 M3.7 直接相关的覆盖包括：

- 视觉输入：PNG/JPEG/WebP 魔数、规范 base64、空数据、超限、MIME 伪装、额外字段和单图数量限制。
- 聊天输入：字符串兼容、消息对象、纯图片占位、未知字段和落库前拒绝。
- Magpie 视觉驱动：精确模型检查、`image` 能力声明、输出上限、非流式响应、有限重试、超时、取消、协议错误和错误脱敏。
- 聊天闭环：视觉成功后单独调用聊天模型；视觉失败不调用聊天模型；纯图片历史不保存转述；视觉与聊天两次额度预留。
- 存储迁移：schema v6 → v7 保留历史 `model_calls`，并允许 `vision` purpose；视觉审计不得关联助手消息。
- 生命周期：完整视觉配置配 mock 模式时，在打开存储和注册定时器之前拒绝启动；启动报告在视觉关闭时报告 `visionEnabled=false`、`visionProvider=null`、`visionModel=null`。
- 网页和 SSE：图片控件、带图聊天事件顺序、未知字段拒绝和鉴权失败不落库。

自动测试不读取真实人格文件，不调用真实视觉或聊天模型，也不操作正式数据库。测试图片是固定的小型合成 fixture。

## 3. 真实 4100 验收

测试只使用隔离的 4100 测试 Profile，正式 4096 实例未操作。视觉配置只存在于仓库外的测试 Profile：

- 视觉模型：`kano/gpt-5.6-luna`
- 聊天主模型：`deepseek/deepseek-flash`
- 验收图片：`F:\kanobot\dsh\vision-acceptance.png`，内容为 `KANO 2026`，不属于仓库

成功路径结果：

- SSE 事件顺序为 `vision, ready, delta..., done`，视觉阶段先完成，聊天正文才开始输出。
- 主模型最终回复 `KANO 2026`。
- 数据库最新两条模型调用分别为：
  - `vision`：`kano/gpt-5.6-luna`，`succeeded`，`attempts = 1`，`assistant_message_id = NULL`。
  - `chat`：`deepseek/deepseek-flash`，`succeeded`，关联当轮助手消息。
- 用户正文只保存配文，不包含图片 base64 或视觉转述。
- 扫描主库、WAL、SHM 和独立墓碑库文件，均未发现验收图片的 base64。

失败路径结果：

- `antigravity/gemini-3.8-flash` 实测返回 403，原因是账号地区/资格不满足；插件记录 `vision_auth_failed`，没有调用聊天模型。
- 直接探测确认 `deepseek/deepseek-v4-flash` 和 `kano/gpt-5.6-luna` 都能读出 `KANO 2026`；`kimi/kimi-k3.1-pro` 返回 401。路由可用性不等于插件已把它们设为默认模型，模型仍完全由测试配置决定。
- 首次真实回复曾错误声称“没收到图片”。修正后，视觉提示块明确说明系统已经读取附图并要求依据转述回答；重新验收通过。这证明提示契约需要显式表达，而不能假设主模型会自行理解。

## 4. 边界与未完成项

- M3.7 只完成视觉输入模块。完整 M3 仍缺：不经过 DSH 的本地开发入口、跨聊天/记忆/模型的统一审计视图、风格检查失败后的自动重生成，以及真实模型场景比较。
- 视觉模型没有自动选型、自动切换或厂商兜底。未配置时带图请求在落库前失败；配置后只调用指定模型。
- 当前只支持本机回环 Magpie `/v1`，不支持在插件里直接填写任意远程第三方 URL。需要第三方模型时，先在本机 Magpie 中配置路由。
- 每条消息只支持一张图片；不支持视频、音频、PDF、远程图片 URL 或多图对照。
- 视觉转述是模型生成的不可信观察，不等同于 OCR 或事实来源。重要文字仍需人工核对，不能让图片中的指令改变系统规则。
- 图片不持久化意味着重启后不能重新读取历史附件；这是当前隐私边界，不是遗漏。若以后需要保留图片，必须单独设计加密、保留期、删除和所有者审计。
